# wxbot

基于 Windows UI Automation 的个人微信自动回复工具：
默认监听主窗口全部会话：私聊新消息和群聊消息 → SQLite 队列与连续消息合并 → Butler/模型处理 → 自动回复（群内按成员区分会话）。

可选的 [Telegram 频道窗口转发与图文投递](docs/TELEGRAM_RELAY_SKILL.md) 默认关闭，与微信共用主窗口模式的单一 UI 调度线程；启用前需配置现有机器人、频道及微信图片控件，异常结果需人工核对。

> ⚠️ 非官方用法，有账号风险。建议用小号，只绑定少数好友，保持低频。

```

    ├── inbox.py            # UI 线程采集、快照、群提及过滤和发送调度
    ├── queue_store.py      # SQLite 收件、合并批次、发件、恢复与运行锁
    ├── queue_worker.py     # 单个后台模型线程
    ├── queue_admin.py      # 队列状态查看与异常任务恢复命令
    ├── delivery.py         # 发件执行与新消息气泡确认
    ├── config.py           # 读取配置
    ├── log.py
    ├── state.py            # 新消息检测（对比前后两次消息列表）
    ├── wechat/
    │   ├── locator.py      # 按配置条件查找控件
    │   ├── main_window.py  # 主窗口会话发现、切换、标题与焦点校验
    │   ├── clipboard.py    # 剪贴板格式备份、序号校验、恢复与重试
    │   ├── typing.py       # 每 5 字、间隔 0.5 秒的分批粘贴与输入校验
    │   └── chat_window.py  # 共用消息读取、头像识别、输入准备；独立窗口定位
    └── processor/
        ├── base.py         # 处理器接口 + Echo 调试处理器

        ├── ollama.py       # 本地模型（Ollama）
        └── router.py       # /命令 路由
```

## 使用步骤

默认使用 **主窗口模式**（`[wechat].mode = "main"`）：保持微信主窗口打开，程序扫描左侧会话列表的 `[N条]` 未读标记，自动点击聊天并读取右侧消息。标题末尾的人数括号用于识别群聊；群聊消息全部接收并进入 AI 上下文，被 `@机器人昵称` 时必定文字回复并 @发言人，普通消息按 `group_reply_chance` 概率回复，回复时按 `emoji_chance` 二选一（文字/表情图），未抽中则静默（已进上下文不发送）。正在右侧打开的会话也会持续检查，避免已读状态下漏收新消息。主窗口模式可以不填写绑定列表，`listen_all = false` 时才将绑定列表作为监听范围。

主窗口模式的首次连接：仅处理该会话的未读消息，不重放其余历史；此后按每个会话的消息快照去重。空闲轮询仅读取 UIA 已暴露的会话行，不激活窗口、移动鼠标或滚动；当前聊天只在微信位于前台时读取截图。只有存在待采集未读消息、恢复核对或实际发件时才选择会话，寻找目标最多扫描 `max_scan_pages` 页。UIA 没有暴露的屏外会话不会为轮询而主动滚动补扫；超出已加载消息区的历史也不自动向上补读。实际收发会占用微信界面和键盘焦点，每批键入与回车前均核对对象及焦点。

扫描发现同名会话时会阻止该名称收发，请通过不同备注或群名区分。已采集的会话类型和模型回复目标保持一致，私聊/群聊类型变化时停止处理。消息控件暂时不可读时保留快照与未读任务；输入框已有草稿或无法确认是否为空时停止发送，保留原内容。

收到明确未读消息时，即使右侧已经是该聊天，也会主动点击一次会话列表中的对应行，再读取消息；控制台打印「已主动点击未读会话行」。未读任务先持久化，再点击会话，避免清掉角标后丢失收件线索。无未读的当前面板采集仍只读，发送中的只读轮询不会点击会话行。

`[wechat].mode = "independent"` 可切回原来的独立窗口模式。已有独立窗口的绑定对象在主窗口模式下也兼容读取。现有本地配置省略 `mode` 时默认使用 `main`，重启 wxbot 后生效。Butler/Hermes 接口和角色绑定仍按会话名匹配；自动发现的新对象未配置 Butler 身份时，沿用 Butler 的 default Profile 回退规则。

在 log 管理台的共享目录中维护私聊／群聊监听名单和机器人昵称（可多个）；旧 `[bot]` 字段通过 `python -m butler migrate` 导入 `data/business.sqlite3`。允许收取的群消息先存入同群公共上下文；本地规则决定文字、表情或静默，静默和表情批次无需调用模型。每个已绑定成员保留独立会话与有权限访问的长期记忆。固定用户身份请在 log 的“用户与记忆”中用头像和昵称建立；头像哈希是收件观测信息，昵称映射仅辅助显示，不会自动授予个人记忆权限或选择 @ 收件人。联系人和群聊标题不要重复。

主窗口模式收件时，会用会话列表里的「群昵称: 消息摘要」与最后一条收到的消息核对；正文完整匹配后，自动保存该群的 `member_id → 群昵称` 映射到共享目录数据库，后续消息和重启后继续复用。不同群的映射独立，手动配置的昵称优先。摘要截断、消息不匹配或最后一条是自己发送的消息时不建立映射。实际收件头像按窗口 DPI 截取紧贴头像的 36×36 布局区域，再使用与管理台上传相同的标准化算法；采样失败保留为未知身份。头像变化不改变已建立的固定用户 ID。

### 真正微信 @ 的识别与校准

首段群回复单独保存已确认绑定的目标昵称，正文不拼接文本 @ 前缀。发送时输入 `@` 后继续输入完整群昵称，全部可见候选只有一个且精确匹配时点击，核对输入框中的嵌入提及对象，最后输入正文和确认自己的新气泡。候选缺失、多个或选择器不可读时，清理本次输入的 `@昵称` 并确认输入框为空，转为纯正文发送；清理失败、焦点变化、用户草稿冲突或无法核对的嵌入对象仍停止并保留内容。气泡确认仅表示机器人已发送，不代表已核验对方收到提醒。

默认会记录输入 `@` 前的顶层窗口与可见列表，随后在**新出现、同一进程、由当前聊天 HWND 直接拥有**的弹窗，以及当前聊天中新出现的可见内嵌列表中寻找候选；已有会话/消息列表、其他聊天或其他程序的列表不会参与选择。仍无法识别时，使用本机探针读取准确控件后，可配置以下无凭据模板：

```toml
[wechat.mention.panel]
name = "替换为本机探针读到的 @ 选择器准确名称"

[wechat.mention.item]
control_type = "ListItemControl"
```

自动发现失败时，改为清理本次查询并发送纯正文，现有流转日志记录回退原因。只有核对过嵌入对象才声明真正提及成功，配置选择器不能绕过该校验。当前实现经过假 UI 的离线验证；本机实际界面仍需在用户授权后验证。此前已阻断的旧任务须在核对发送结果和清理残留草稿后手工重试或丢弃；开发和升级过程不自动重启服务。

### 1. 安装

需要 Windows 10/11、Python 3.14+。

```bash
pip install -r requirements.txt
python -m butler setup
```

向导支持本机 Codex、已有 Butler，以及 Hermes、OpenClaw、Cursor、DeepSeek 和自定义 API 的直接接入。
默认值来自代码，已有配置不覆盖；自动化初始化可用 `python -m butler init`。
模式、登录与升级步骤见 [安装文档](docs/CODEX_INSTALL.md)。直接接入不提供 Butler 业务工具。

### 2. 校准控件（必做）

`config.wxbot.toml` 里 `[wechat.*]` 的控件定位已按微信 4.x 校准，版本变化时按本机控件调整：

1. 在微信里双击一个联系人，打开独立聊天窗口
2. `python tools/probe.py --list`，确认窗口标题和类名
3. `python tools/probe.py --window 联系人名 --depth 12`，查看控件树
4. 找到：消息列表（通常是 ListControl，子项是一条条消息）、输入框（通常是 EditControl）、
   消息条目里的头像（通常是 ButtonControl），把对应特征填进配置

探测默认脱敏，输出可以放心贴给别人分析。

### 3. 先用 echo 模式测试

`config.wxbot.toml` 里设 `backend = "echo"`，运行：

```bash
python -m wxbot.main
```

仅在使用者明确授权后，让测试联系人发一条消息，机器人应回复"收到：xxx"。核对收发后恢复向导选择的后端。

## 工作原理

- 主窗口模式自动发现未读会话、选择并核对右侧标题；独立窗口模式按绑定列表轮询各窗口
- 群聊接收其他成员发出的全部文字消息并进入 AI 上下文；被 @ 时文字回复并 @发言人，普通消息按 `group_reply_chance` 概率回复，回复时按 `emoji_chance` 二选一（文字/表情图），未抽中则静默
- 群聊按成员（头像感知哈希）区分会话与记忆，每人独立上下文；每条进入模型的消息会带发言人和成员 ID 标签；命令仍按原文本路由
- 对比上一次的快照找出新消息；微信 4.x 不暴露头像控件，所以截取消息条目，按头像在左/右判断是对方还是自己发的
- 首次采集只处理未读消息，其余历史作为快照；之后按持久化快照识别新增消息
- 消息和快照在同一 SQLite 事务落库；单个后台线程调用模型，等待模型时 UI 线程继续收件
- 按会话合并连续消息：默认安静 3 秒或累计等待 10 秒成批；不同会话不混合，群内不同成员及命令单独成批
- 就绪批次按顺序处理；同会话旧批次的回复确认发送前，其补充消息继续收集，等待下一批；其他用户可继续处理
- 发送时激活目标会话、点击输入框，每 5 字通过 Ctrl+V 粘贴一批，批次间隔 0.5 秒，全文校验后只按一次回车。正文作为 Unicode 剪贴板文本传入，标点、emoji、换行及 `{Enter}` 等字面文本保持原样，不再逐字模拟正文按键
- 每批粘贴前备份原剪贴板的可安全复制格式，读回该批内容后恢复；期间用户复制了新内容时保留新内容。剪贴板无法安全备份、写入失败或粘贴内容不符时停止发送，保留草稿；恢复暂时失败时由 UI 循环继续尝试，不自动回退到逐字键盘输入
- 剪贴板版本在关闭写入后、确认所有者仍为 wxbot 时记录；粘贴前核对版本和所有者，避免写入结束时的序号变化被误判为外部复制。目标会话变化、输入失焦和剪贴板校验失败分别记录原因；旧 `blocked` 不会因重启自动解除
- 每批读回输入前缀，回车前核对全文；发现内容错乱、不可读或焦点变化则停止并保留草稿。回车前最后一次读到的新消息先入库，再保存发送确认锚点，避免发送期间的补充被跳过
- 回车后看到新增的自己消息气泡才标记已发送；无法确认或中断时等待核对，不自动重发。发件异常从首次失败起满180秒后自动丢弃该句，保留原文与记录

## 队列配置与恢复

队列用于 `mode = "main"`。无需添加配置即可使用默认值；`mode = "independent"` 保留原收发循环。可在 `config.wxbot.toml` 调整：

```toml
[queue]
database = "cache/wxbot_queue.sqlite3"
max_model_requests = 2
quiet_seconds = 3.0
max_wait_seconds = 10.0
confirm_timeout = 5.0
```

例如 A 连发「你好」「我想问个问题」，中间 B 发来消息：A、B 各自计时合并，谁先就绪谁先排队。模型已开始处理 A 后收到的补充进入 A 下一批。10 秒是合并等待上限，模型排队、执行和键入时间另计。群内仅连续来自同一成员的消息合并，不跨其他成员或命令合并。

默认最多两位用户同时等待模型，`max_model_requests` 可设为其他正整数。等待期间继续采集其他会话；同一用户上一轮所有分句结束后才提交其下一轮。界面每次完成一次会话采集或一句话的键入、回车及确认，两类任务都有积压时交替处理；键入和确认期间不切换会话。采集失败保留任务，并按轮询间隔再试。

Butler 完整生成、处理行动与补发后一次返回全部分句，wxbot 原子保存。A 三句、B 两句都就绪时按 A1 → B1 → A2 → B2 → A3 发送；B 后到时等当前一句确认后参与轮转。每句仍以 5 字/0.5 秒键入，句号、问号、叹号和普通换行可分句；逗号、小数、URL 和代码区不误拆。旧 Butler、其他模型后端、本地命令及主动推送保留单条语义，独立窗口模式仍发送完整回复。

数据库默认位于项目的 `cache/` 中，保存消息正文和回复，已加入 Git 忽略。启动日志会打印恢复结果和当前数量；运行日志包含采集、批次就绪、模型开始、回复入发件箱及发送状态。查询命令可在 wxbot 运行时执行，不操作微信界面：

```powershell
.\.venv\Scripts\python -m wxbot.queue_admin status
.\.venv\Scripts\python -m wxbot.queue_admin list --limit 20
```

`list` 显示任务 ID、会话、状态、字数、分句序号/总数、整轮进度和错误，不打印正文。新分句 ID 为 `批次ID:句内序号`，旧发件 ID 保持不变。需要指定配置时，在子命令之前加 `--config 路径`，或用 `--database 路径` 直接选择数据库。

也可在 log 看板的 **「收发队列」** 页查看相同队列，按用户/状态筛选，查看原始阻塞原因、倒计时与失败记录。异常任务旁直接提供 **重试 / 确认已发 / 立即丢弃** 按钮，点击后需确认实际微信发送结果；恢复命令仍可展开复制。**「全部配置」** 页支持按来源编辑配置、恢复默认和保存，密钥只可明确替换/清空、不回显原值；保存会备份并检查版本冲突，页面注明需自行重启哪个服务。查询保持只读。

页面顶部的 **「删除所有未发送成功消息」** 面向微信和 Telegram 的全部会话，不受筛选和分页影响。确认后先备份数据库，再删除未成功的发件、待合并消息和未完成模型批次；旧模型回复和清理前已受理的推送不能重新生成被删除的任务。已发送成功的消息及其必要记录、用户、订阅、记忆、提醒和配置保留。备份位于各队列数据库同目录的 `backups/`。

正在键入、等待发送确认或已提交 HTTP 投递的任务本次保留，页面返回实际删除数量和保留数量；同轮其余待发分块仍会删除。尚未实际采集的微信会话属于读取任务，也会单独计数保留；它们尚未进入消息库，后续新消息继续正常接收。微信输入框中的残留草稿须自行清理。部分成功的回复和图文包保留原始分块数量及取消回执，不会因删除剩余分块而被误记为全部成功。使用此功能需自行重载 **wxbot、log 和 Telegram 接收器**，并强制刷新浏览器；程序不会自动重启服务。

文字行被裁剪、暂时无法确认发送方时，采集会保留快照和待重读任务，发送流程独立核验目标会话及自己的新增气泡。读取发送目标的消息列表失败或会话对象无法确认时，仍停止发送。

「wxbot 通道」还提供 **「只看消息流转」**：wxbot 收件入库 → 合并/阻塞 → Butler 接收 → Hermes 工具进度与最终结果 → 分句发送。联系人与批次 ID 精确关联，未到 Butler 的消息也会显示；阶段缺失标记未确认。该链路记录功能同时改动了 wxbot、Butler、log 及 Hermes 的可选最终正文事件，需先停 wxbot，重启更新后的 Hermes、Butler、log，再启动 wxbot；旧异常任务仍保留。详见 [log 说明](log/README.md)。

| 状态 | 含义与处理 |
|---|---|
| `ready` / `processing` | 待提交 / 已提交，等待模型完整回复 |
| `waiting_delivery` | 完整回复已就绪，等待所有分句发送确认 |
| `pending` / `sending` / `confirming` | 发件等待 / 分批粘贴 / 回车后确认 |
| `blocked` | 会话不可用、类型/名称歧义、已有草稿、输入内容不可读/校验不符或焦点变化，发送已停止 |
| `uncertain` | 模型调用异常或进程中断，或回车后未确认新增气泡；需核对原操作结果 |
| `done` / `sent` / `skipped` | 批次结束 / 发件已确认 / 已跳过（人工或失败超时） |

异常任务只阻止它所属会话继续处理，其他用户可正常处理。先核对微信、Butler 日志和是否存在输入草稿，再按实际结果操作（将 `<ID>` 替换为 `list` 显示的任务 ID）：

```powershell
# 发件已送达：人工确认，无需再键入
.\.venv\Scripts\python -m wxbot.queue_admin sent <发件ID>
# 确认需要重发：先清理目标输入框中的残留草稿
.\.venv\Scripts\python -m wxbot.queue_admin retry <发件ID> --delivery --acknowledge
# 模型请求需重新执行（可能再次执行提醒等工具）
.\.venv\Scripts\python -m wxbot.queue_admin retry <批次ID> --acknowledge
# 放弃异常任务并继续该会话；发件任务加 --delivery
.\.venv\Scripts\python -m wxbot.queue_admin skip <ID> --delivery
```

人工操作允许 `blocked` / `uncertain` 任务，以及超时后已为 `skipped`、但仍有草稿待人工清理标记的发件任务；先核对发送结果并清理输入框，再重试、确认已发或丢弃以解除会话暂停。已有发件结果的批次应处理发件任务，不能重跑模型。重启时未开始的任务继续排队，执行中断的模型批次转为 `uncertain`；发件先只读核对，能确认已有新气泡的标记完成，其余保持 `uncertain`。模型确认未提交时最多尝试3次；网络超时、进程中断等未知结果不重放，失败最多阻塞180秒（由 queue.failure_discard_seconds 配置），随后保留记录并结束旧批次，放行新消息。详见 [模型失败恢复](docs/LOG_DASHBOARD.md)。

多句回复中某一句异常只暂停所属用户，其他用户可继续。`sent`/`skip`/`retry --delivery` 仅处理指定一句，再重新计算整轮；已确认的句子不重发，也不重跑模型。全部句子 `sent`/`skipped` 才完成整轮并释放该用户下一批。

### 发送失败最多阻塞3分钟

- 发件任务的 `blocked` / `uncertain` 从首次失败开始按 `queue.failure_discard_seconds`（默认180秒）计时，到期将该句标为 `skipped` / `resolution=timeout`，原文与历史保留。没有发件结果的模型异常批次也使用这个最长阻塞期限；结果未知时不重放原请求，到期结束旧批次并放行后续消息。
- `failed_at` 持久保存，重试和重启不重置；人工重试进入待发送或正在发送后不会被超时流程打断，再次失败时继续使用原期限。
- `[发送失败]` 日志包含任务ID、阶段、失败原因及可读取的目标会话/类型、前台窗口句柄、焦点、已输入字数和是否尝试回车。`[发送超时丢弃]` 明确记录自动结束及原失败原因。不会记录剪贴板或未发送草稿正文。
- log → **收发队列** → 选择用户：异常任务旁有三个操作按钮及倒计时，下方 **发送失败与人工核对记录** 展示最近50条记录。操作只允许异常任务，页面状态过期会拒绝并提示刷新。
- 本次需由用户自行重启 **wxbot → log**；wxbot 取得运行锁后升级为队列版本3，旧失败任务按已有失败时间补记，已经超过180秒的任务会自动丢弃。无需为本次改动重启 Butler 或 Hermes。

输入节奏也可在log的「全部配置 → wxbot · wechat」修改：`wechat.typing.chunk_size` 默认5字（1–100），`chunk_interval` 默认0.5秒（0.05–10）；发送前仍校验内容、目标及焦点。参数保存到wxbot配置后自行重启生效，现有实际参数不会因代码更新而被改写。Hermes调用地址在「Butler · hermes」，修改后自行重启Butler；更多保存及备份规则见 [log说明](log/README.md#配置编辑与生效)。

数据库自动增加 `submitted_text` 字段，保留原模型正文 `text`，记录回车前核对过的实际输入正文；恢复优先按实际输入确认。旧版因输入法导致实际正文改变、但用户已确认发送的任务，可登记实际正文并保持 `uncertain`，等待新版本重启后只读核对。登记本身不释放旧进程队列，也不重发消息。

队列保护已采集的数据；未加载的聊天历史、发送方无法识别以及 UIA 无法区分的完全相同消息仍有局限，不保证微信全量消息无遗漏。不要删除数据库来解除异常任务，否则会丢失队列与快照。

更新后请先停止旧 **wxbot**，再自行重启 **Butler 和 wxbot**；Hermes 无需为本功能重启。新版 wxbot 在取得运行锁后用单事务升级队列，保留旧 ID、正文、状态、时间、确认快照和实际输入；旧待发回复按一整条保留，不重新分句。查询命令使用只读连接，兼容旧库且不会迁移；旧库上的恢复命令会要求先升级。不要同时运行新旧两个 wxbot。

### 分批粘贴修复（2026-10-18）

已使用上述队列版本的部署，本次输入方式修复只需自行重启 **wxbot**；Butler、Hermes 无需为此重启。log 的「全部配置」已同步输入方式说明，需重新加载 log 服务后显示新说明，不影响 wxbot 实际发送方式。原有 blocked/uncertain 任务与草稿不会自动清除或重发，按队列页提示核对后处理。

离线用例覆盖输入及剪贴板异常，实际微信收发需由用户重启后观察。如果退出时其他程序持续占用剪贴板，最后一次恢复仍失败会输出警告；强制结束进程也无法保证恢复。

## 注意

- 运行期间微信收发窗口要保持完整可见，不能被遮挡或最小化，电脑不能锁屏
- 空闲轮询不滚动或抢焦点；实际选择未读对象、发件或恢复核对仍会操作界面，尽量不要同时在微信打字
- 微信更新后控件可能变化，重新用 probe.py 校准即可
