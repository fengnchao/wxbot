# 用户、记忆、群上下文与微信提及

## 管理入口

log 左侧“用户与任务 → 用户与记忆”。每行依次显示头像、永久用户 ID、群名－群昵称／私聊昵称、“查看记忆”按钮。

新增用户时填写会话类型、微信实际会话名称、昵称，并上传单独的头像截图。接受 PNG/JPEG/WebP，最大 512 KiB、400 万像素；服务端重新编码为标准 36×36 PNG，移除元数据。用户 ID 使用随机 UUID，与头像哈希及昵称无关；初始记忆为 0 条。

可以给已有绑定补充不同头像，改昵称，或停用。相同昵称或头像不会自动合并不同用户。群成员须通过头像参考或管理员确认的观测 member_key 识别；未知或歧义身份仍可参与公开群上下文，但不能读取或写入个人长期记忆。

收到消息时自动建档，不依赖模型是否回复。首次头像和昵称证据一致时创建独立用户 ID、头像参考和空白记忆；同群证据一致时复用该身份，不跨群或私聊自动共享。同头像但昵称明确冲突会建立独立待核对档案，不能读取已有用户的记忆。缺少头像或昵称、头像辨识度不足时先待核对；没有昵称显示“待命名”，不会拿占位昵称执行真正 @。无法取得任何稳定身份线索时不反复创建随机用户。

自动观测的成员 key 只用于去重，不直接授予个人记忆权限；后续暂时缺头像或昵称时保留档案 ID，但本次请求降为待核对。管理员确认待核对身份后，只把不与其他档案冲突的观测 key 用作人工识别依据。

在 log 可筛选“待核对”、查看观测成员 ID、编辑昵称和头像，并保存确认身份；手工新增、修正记忆和关联共享的权限继续保留。停用用户不会因再次收到消息而自动恢复。

旧版直接编辑 `[wechat.group_sender.member_names]` 只改变旧观测昵称，不等于授权新的永久用户身份。请通过此页面上传实际头像、核对绑定；群列表参考图与聊天行采样不能直接用同一原始截图哈希猜测身份。

消息行头像裁剪按 DPI 换算为标准 36×36；需要校准时可在 `[wechat.group_sender]` 设置 `identity_avatar_left_offset`（默认12）及 `identity_avatar_top_offset`（默认0），log 配置管理提供相同字段。

## 手工关联与记忆

默认每个群成员／私聊绑定分别创建用户和记忆空间。只有管理员在“编辑绑定 → 手工绑定为同一用户”中明确选择目标并确认，才共享长期记忆；模型 Thread、角色、聊天历史仍按绑定分别保留。

预览会展示两侧身份、记忆数量及同名 key 冲突。每个冲突需选择保留来源或目标；确认前版本发生变化时拒绝覆盖，重新预览即可。关联群身份到私聊身份意味着该群身份可以使用所关联范围的私聊长期记忆，页面会明确提示；不会把其他群成员的私人记忆加入公共上下文。

“查看记忆”支持新增、修正、删除、搜索和分页。修改记录可查看来源、时间与变更。记忆变化会更新版本，使后续模型请求切换会话范围，避免继续沿用旧会话的已删内容。审计为管理员保留历史，不参与模型召回。

微信里仅允许已开启 `butler-memory` 的身份使用记忆工具。模型只能操作 Butler 为本次请求绑定的身份，不能传 uid／owner 切换用户。用户明确说“忘掉某条记忆”时，模型可使用 `memory_delete`；心跳仍只有读取权限。

手工关联只共享长期记忆；提醒的查看、取消与创建权限仍按各自绑定隔离，避免群身份操作私聊提醒。可明确确认归属的旧提醒迁移到原会话对应的绑定。

旧记忆在服务端能够明确确认旧 owner 与新绑定的关系时复制到新范围，旧数据保留。冲突不会静默覆盖；无法确认的旧群身份不按昵称自动迁移。业务库新增身份表前会创建 SQLite 一致性备份，保存在业务数据目录的 `backups/`。

自动观察创建的新群身份不凭旧头像哈希导入历史私人记忆；只有经管理员确认或手工绑定后，才允许迁移明确归属的旧资料。身份确认字段升级前同样创建备份。

## 群上下文与请求消耗

群成员独立模型会话，回复时补充同群近期公开片段；默认最多最近 30 条、正文合计 6000 字符。当前请求和未来消息不重复带入，其他群内容、其他成员长期记忆、私聊正文不进入公共片段。

目前公共片段保留群成员的入站消息，尚不包含机器人自己的已发回复；机器人自己的回复仍在对应成员的独立会话中。

在 Butler 配置的 `[context]` 可设置 `group_messages`（1–200）和 `group_characters`（1–30000）；log 配置管理提供相同字段。

公开消息按队列来源 ID 幂等归档；同一请求使用固定快照。仅完整成功的模型轮次推进消费位置；结果未知的请求不因此重新执行。换 Thread 后重新提供有界近期上下文。

新文字行的发送方暂时无法确认时，保留原快照和未读任务，等待重新识别，不先把文字消费成旧消息。微信窗口遮挡、头像行被裁切时可能出现这种情况。初次接入仍不回复历史消息，发送方抖动也不会让历史消息反复入队。

静默群消息只归档，不调用模型。只发表情的批次直接进入已校准表情投递；文字回复才调用模型。群内仍按队列顺序投递，不并发操作微信。

普通插话限制可以在 `[bot]` 配置：

```toml
group_reply_cooldown_seconds = 30
group_reply_budget = 10
group_reply_budget_window_seconds = 600
group_continuation_seconds = 120
```

明确 @、直接叫机器人、命令和可确认的同成员续问优先于随机插话限制。这里是请求数预算，不是实际费用统计。

## 微信真正 @

发件箱单独保存正文与 `mention_name`。只有服务端已确认的群成员回复才设置首段提及；私聊、新闻、普通主动推送不会自动加 @，后续分段不重复提及。

微信发送状态机会先输入 `@`，继续输入完整群昵称，再检查候选。全部可见用户中只有一个、昵称精确匹配且可选时才点击，并读取输入框中的真实提及对象，再粘贴正文。不会把普通 `@昵称` 字符串当作提及成功。

默认自动发现本次触发后新出现、同进程且由当前聊天窗口拥有的弹出层，也识别已确认聊天控件树中新出现的可见候选列表。原有会话列表、消息列表不参与选择。如果微信版本仍无法自动发现，可用本机控件探针确认选择器后配置：

```toml
[wechat.mention.panel]
name = "填写本机探针看到的 @ 选择器名称"

[wechat.mention.item]
control_type = "ListItemControl"
```

以上名称是待填写的示例，不是可直接使用的校准值。控件树须属于已确认的目标聊天。候选有两个或更多、找不到用户或选择器无法读取时，撤掉程序本次输入的 `@昵称`，确认输入框清空后直接发送正文；log 记为“未提及，已转纯正文”。候选有一行无法读取昵称时也不视为唯一匹配。

清理分步执行，每步确认聊天对象、焦点和完整草稿。用户修改过草稿、焦点变化、清理失败或遇到无法核对的嵌入对象时，保留内容并停止，不删除未知内容。可读取的普通 `@昵称` 不冒充提及对象，清理后只发送正文。气泡确认只表示本机发送结果，不声称验证了收件人通知到达。

升级不会自动重放此前已阻断的任务。重启 wxbot 后，先核对并清理微信中残留的旧 `@` 草稿，再在“收发队列”对需要的旧任务选择“重试”；不需要的旧回复可选择“立即丢弃”，释放草稿阻断。

旧版纯文本前缀任务不凭昵称推测新身份。尚未发送且无法确认的旧任务保留原文、标为需人工核对；已开始或结果不确定的任务不改写、不自动重发。队列升级前生成备份，不由 log 查询触发迁移。

## 现有工作流

复用“实时工作流／消息流转”，增加固定用户及绑定、记忆读取数量、公共上下文范围、静默／触发原因、提及对象及气泡核验阶段。流程日志不保存记忆正文、检索结果或头像图片。无模型调用的消息显示归档／静默，不伪造模型完成事件。

## 生效与验证

源码更新后需使用者自行重启 Butler、log、wxbot 并刷新页面；程序不会自动重启现有服务。业务与队列迁移分别由所属服务启动执行，不复制个人 Codex 认证或其他安装的数据。

wxbot 启动时从保存的收件快照和最多 500 条最新成员头像观测同步用户身份，不提交历史正文、不重放旧请求、不产生发送任务。同一会话按批次登记，当前快照识别失败也不会漏掉已经采集过的头像。工作流默认展示“最近消息”，包含已静默归档的消息；可单独切换“进行中”或“异常”。历史结果不确定的卡片保留供核对，不表示模型仍在执行。

主图默认不把“异常”记录挂在服务节点里。异常仍可在右侧查看；点击某条异常时，主图才显示它的历史位置与路径。

本次自动验证使用临时数据库、假模型、假 UI 和假剪贴板；未发送真实微信消息。真实 @ 在不同微信版本的窗口／TextPattern 可访问性仍需本机检查；真实发送验证需另行明确授权。
