# 联系人统一设计

日期：2026-10-30。状态：用户已批准，代码及离线验证完成；现有安装尚未停机迁移，运行数据未切换。

## 用户要求

- 所有联系人整合到一个地方，结束不同页面、配置文件各存一份名单的情况。
- 用户本轮明确修正身份规则：同名不用隔离；记录联系人在哪个群、在该群使用什么群昵称。
- 用户先审阅详细方案，随后明确批准实施；实际安装按人工停机流程切换。

## 采用的方向与取舍

推荐沿用现有 `data/business.sqlite3`，作为本机安装的联系人唯一数据来源，管理台只保留一个「联系人」入口。联系人新增、改名、监听、角色/心跳、订阅与记忆都从这里维护；其他模块读取同一套服务接口。

已有目录、身份和记忆就在该数据库中，因此继续集中到它最符合当前架构。统一成 JSON 仍需与身份/记忆数据库同步，会形成两个来源；保留各个文件再同步也会保留重复写入和冲突，不能解决本次问题。草案据此选择现有 SQLite，无需引入外部服务或新依赖。

## 现状与重复来源

| 当前来源 | 当前内容 | 统一后的处理 |
| --- | --- | --- |
| 数据库 `directory_state.contacts` | 会话名、uid、Profile、显示名称、会话键 | 迁为统一联系人和会话关系，保留旧路由值 |
| `directory_state.channel.bot.bound_users/bound_groups` | 私聊、群聊监听名单 | 迁为会话的监听开关，兼容列表只在读取时生成 |
| `directory_state.aliases`、队列库群昵称缓存 | 群、成员观测 ID、昵称 | 迁入统一的群成员/昵称关系，队列只保留运行所需缓存 |
| `butler_heartbeat.json` | 以名称为键的角色、Skill 白名单、心跳开关 | 迁入数据库内的联系人/会话策略关系 |
| `butler_groups.json` | 新闻、问候、其他类型的订阅名单 | 迁入数据库内的订阅关系 |
| `user_profiles/user_bindings` 等身份表 | 固定 ID、群成员身份、头像、记忆范围 | 复用和关联，不再作为另一套可单独新增的联系人名单 |
| 旧 TOML 的联系人、监听字段 | 未迁移安装的旧来源 | 一次性导入后停用，以迁移账本标记 |

这是一次存储和入口的整合，不只是把原来的几个表单放进同一页。日志、已发送记录、提醒任务和新闻正文仍属于各自业务数据，不当作新的联系人主数据来源。

## 统一后的对象与关系

### 1. 联系人：以人为单位

每个人一个稳定的 `contact_id`、一个常用姓名、一份个人记忆。复用合适的现有固定用户 ID，其他旧 ID 建立跳转关系，避免历史引用失效。姓名可以修改，固定 ID 不随之变化。

同名的已命名记录归入同一联系人，跨私聊和不同群共享该联系人的档案与记忆。姓名匹配采用去除首尾空白和 Unicode 标准化后的精确匹配，不使用模糊相似度。来自真实群昵称的相同名称也按此规则归并。不同群昵称通过联系人下的成员关系关联到同一人。迁移时先继承已经共用 user_id 或人工关联的关系；缺少既有依据时，在联系人页通过“关联已有群成员/新增所属群”明确指定，不根据不同昵称的相似程度猜测。

当前常用姓名和各群当前有效昵称参与同名匹配；历史名称保留用于搜索、旧记录追查，不作为新观测的自动合并键。改名后成员关系继续引用原固定 ID。若新名称已属于另一联系人，保存前展示同名归并预览，确认本次更名后按既定同名规则合并。这些匹配细节为本方案建议的默认值，供用户审阅。

空姓名、系统生成的“成员-哈希”等占位名称不作为同名合并键；它们属于待补充姓名的观测记录。补齐姓名后按统一规则归入联系人。头像仍作为识别线索保存，不取代联系人 ID。

### 2. 会话与群：保存实际收发位置

私聊窗口和微信群各有稳定的会话记录，保存微信会话名、类型、原 uid/Profile/会话键以及监听开关。群本身是收发目的地，群成员是人，两者通过成员关系连接。

示例：

- 联系人「小王」：一份档案、一份记忆。
- 私聊：微信窗口「小王」。
- 项目群：群昵称「王工」。
- 同学群：群昵称「小王」。

页面只维护一次「小王」，下面列出这三个位置。需要发送或真正 @ 时，使用当前会话及该群保存的昵称/成员观测信息定位。群昵称本身不再成为额外的一套可维护联系人名单。

同一群若有多个成员观测使用同一个昵称，个人档案和记忆依然按用户要求统一，但各成员观测/绑定关系分别保存。回复当前消息时沿用原发言成员的精确关系；主动任务需要 @ 时必须指定具体成员关系。未指定且存在多个候选时，界面要求补选，已有定时任务标为待补充目标，不任意选择，也不自动 @ 全部同名成员。

同名规则针对人；不同群仍保留自己的会话和成员关系。群消息上下文继续归属所在群，个人记忆归属统一联系人。

### 3. 角色、心跳、订阅：使用 ID 引用

角色/Skill 策略及订阅关系使用稳定 ID 引用联系人或群会话，不再各自保存一组自由输入的联系人名称。

- 联系人详情维护默认角色、允许 Skill 和个人记忆；成员关系可保留当前所在群的信息。
- 现有按会话保存的角色/Skill 和心跳设置首先原样迁入对应会话覆盖项，防止统一后突然改变群或私聊的行为；没有覆盖项时使用联系人默认值。
- 原来对群执行的心跳继续对该群执行；个人心跳必须有明确的私聊目的地。未配置目的地时显示待补充，不把群成员昵称当作可直接私聊的窗口名。
- 新闻/问候等订阅绑定到实际收件会话；同一人订阅私聊和某个群属于两个明确目的地，可分别显示和设置。
- 实际投递阶段只根据订阅的目的地生成任务，联系人归并不额外增加投递次数。
- 全局心跳间隔、机器人昵称、全部监听开关保留为全局设置，它们不再携带第二份联系人名单。

## 单一管理入口

左侧导航保留一个「联系人」入口。进入后可筛选“全部、私聊、群聊、待补充资料、已停用”，并按姓名、群名、群昵称搜索。

联系人详情内统一显示：

1. 基本资料：常用姓名、头像、固定 ID、历史名称。
2. 会话和所属群：私聊窗口、所在群、各群群昵称、监听开关。
3. 角色与心跳：默认角色、允许 Skill、会话覆盖项、心跳开关及运行记录。
4. 订阅：新闻、问候和现有其他类型，显示实际收件位置。
5. 记忆与记录：共享记忆、关联历史、迁移中发现的内容冲突。

群详情展示该群的监听、角色/心跳、订阅与成员列表。点成员仍打开统一的个人联系人。

原「用户与记忆」「角色与心跳」「用户分组」中的联系人编辑入口归入此页；旧链接跳转到对应详情或子页。新闻来源、分类、条数等全局业务设置保留原有能力，但不再维护另一份收件人列表。配置管理仅显示统一来源和入口，不提供可以重新写出旧名单的底层编辑器。

管理台可以展示旧 uid/Profile 等兼容字段，但这些放在高级详情中，正常增改联系人不要求重复填写多份名单。

## 同名合并与旧记忆

现有多个同名用户 ID 归并后，保留全部会话、群成员关系、头像参考、旧 ID、历史记忆和修改记录。选择已有私聊档案作为保留 ID；没有私聊档案时选择创建时间最早的记录，时间相同时按固定 ID 排序，结果必须可重复。

记忆处理规则：

- 不同 key 直接合并；相同 key、相同值去重。
- 相同 key、不同值不静默覆盖。保存全部来源和值，列为该联系人的“待整理记忆”。
- 查询这类记忆时同时返回带来源标记的不同内容，不默选一个值；用户在同一联系人详情中可以决定保留哪一项。
- 联系人已经统一，不因为某个记忆 key 冲突而继续保留两套隔离身份。
- 提醒和已存在的投递任务保留原来的实际目的地；统一身份不把群提醒改投私聊，也不重放旧任务。

同名归并由服务端的明确规则执行，模型提示或用户消息内容不能直接指定其他联系人 ID。现有停用状态不会因姓名匹配自动启用；旧成员观测 ID 和头像参考只随其原关系迁移，不能无依据接到另一段群成员记录上。

## 迁移过程与冲突处理

1. **只读预览**：列出所有现用来源、可归并的同名记录、仅存在于监听/订阅/策略中的联系人、孤立昵称、记忆和策略冲突，以及预期迁移数量。
2. **备份与切换窗口**：使用 SQLite backup 保存完整数据库，备份涉及的旧配置/JSON及摘要。切换前由用户停止相关旧进程，避免旧进程继续写旧文件；程序不自行重启现有服务。
3. **一次性事务导入**：从共享目录、身份表、现用角色/心跳和订阅文件及遗留配置汇总。联系人、ID 引用和迁移账本在同一事务提交。失败整体回滚。
4. **保留单侧记录**：只在监听名单或订阅名单出现的联系人照样导入，保留原来的有效设置；缺少路由资料的标为待补充，绝不因缺少另一个文件中的记录而丢弃。只从被动历史观测导入的联系人不自动开启监听、心跳或订阅。
5. **处理歧义**：同一个收发位置被标为私聊和群聊、多个现用文件对同一会话的策略相互冲突时，预览明确列出。无法原样保留的冲突不擅自选择，待用户在迁移预览确认。只有同名身份和记忆冲突时，按上一节规则归并并保留全部值。
6. **停止重复来源**：迁移标志成功后，本机所有相关读写统一走数据库。旧 JSON/TOML 只留备份，不再回读、双写或由管理台重新生成。未迁移的旧安装继续使用原兼容读取器。
7. **核对后启用**：数量、关联、开关和目的地核对通过，再由用户按提示启动服务。迁移命令可重跑，账本保证不会覆盖已在统一页面做的新修改。

数据库只做增量扩展，先保留旧表及 ID 映射便于追查。回退应恢复同一批数据库与配置备份；已经在新页面产生修改后，要先导出增量再回退，不能把旧数据库直接覆盖上去造成新数据丢失。

## 代码与接口边界

- Butler 服务层负责统一联系人、同名归并、成员关系、策略、订阅、迁移及版本校验；模型后端接口继续只处理模型请求。
- wxbot 只读取会话、监听及成员昵称投影并负责 Windows UI 和投递队列，不持有另一套持久联系人来源。
- log 通过同一联系人服务读取和提交变更，不各自实现 JSON 写入器。
- 给现有 `DirectoryContactMap`、策略读取器和 `GroupStore` 提供数据库适配，确保迁移后的调用方统一取数。
- 同步改造新闻投递、Telegram 新闻转发/机器人新闻分发中的订阅读取；这些调用方不能继续直接打开旧分组 JSON。
- 新闻分类、来源、采集运行状态等非联系人设置保持独立。它们的路径不再依赖“订阅名单必须是某个 JSON 文件”的假设。
- 旧的角色、分组、用户接口作为短期兼容入口时，内部仍委托统一服务；禁止另设数据来源。直接模型/外部 Butler 模式沿用既有能力边界，不在本机生成远端身份或记忆副本。
- 管理接口执行服务端身份和权限校验，并使用版本号拒绝过期编辑；联系人归并不从提示文本中取得授权。

## 实施顺序

1. 统一服务与数据库增量结构，明确个人、会话、群成员、默认/覆盖策略、订阅和旧 ID 跳转。
2. 迁移预览与执行、备份、幂等和失败回滚；先在临时复制数据上验证。
3. Butler、wxbot、心跳、新闻与 Telegram 订阅读取切换到统一投影。
4. 单一联系人页面及旧链接跳转，移除可以重新产生多份名单的编辑入口。
5. 离线回归与迁移核对报告，准备人工切换步骤。实际本机数据切换属于实施后的明确部署步骤。

## 验收标准

- 新增或修改一个联系人只需操作一个入口；监听、角色、心跳和订阅立即引用同一条数据。
- 所有联系人枚举来自统一服务；迁移后运行时不再读写旧联系人名单文件。
- 同名跨群只显示一个人，并能准确查看每个群中的群昵称；个人记忆共享。
- 不同群昵称可以在一个人下面维护，真实 @ 使用所在群的正确成员信息。
- 现有路由 uid/Profile、会话键、心跳开关、订阅目的地、停用状态、提醒和历史记忆都可核对且不丢失。
- 改显示名称不会新建第二人，也不会切断已有角色、订阅和记忆。
- 迁移重跑不重复创建、不覆盖新修改；中途失败不留下半套可用状态。
- 从其他工作目录启动仍读取同一数据库，延续本次已修复的路径规则。
- 离线测试使用临时数据库、假模型和假投递，验证合并、冲突、并发编辑、重命名、删除/停用引用及旧安装兼容；不发送真实微信测试消息。

## 留给实施者的选择

表名、索引、分页参数、前端组件拆分和兼容适配器的具体组织由实施者决定，沿用 Python、SQLite 和现有原生 JavaScript。优先复用身份、记忆及投递能力，不为统一入口重写整套业务。上述同名规则、单一来源、保存目的地、内容不丢失和人工切换要求属于本方案的固定约束。

## 实施结果（2026-10-30）

已实现统一数据库、联系人页面、同名归并、各群成员关系、冲突记忆来源保留、旧接口投影及显式迁移工具。身份、角色、订阅和监听从同一来源读取；实际安装未自动激活。

直接模型和外部 Butler 安装保持原共享目录及本地监听配置入口，避免在本机复制远端身份；本次显式统一迁移仅适用于本机 Butler 模式。自定义联系人库与另一份已有业务库冲突时，预览明确阻止迁移，要求先核对来源，不能忽略另一份数据。
