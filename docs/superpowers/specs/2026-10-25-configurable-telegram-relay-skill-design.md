# 可配置 Telegram 窗口转发 Skill 与图文投递设计

日期：2026-10-25。状态：用户批准后的代码实现与离线验证已完成（2026-10-26）；本机界面校准及真实发送验证尚未进行。

## 目标与现状

用户要求将 Telegram 频道窗口监听和转发做成可配置 Skill，设置频道名称、监听窗口及目标机器人；处理与 wxbot 的鼠标/键盘冲突、多频道积压，以及消息头、正文、图片和链接。

已有 `butler/telegram_bot` 私聊机器人收件、Butler `/v1/telegram/inbox`、文字新闻展开、微信队列与 log 记录。图片只保存 photo/file_id 等元数据，纯图片被跳过。没有已实现的 Telegram Desktop 自动转发器，wxbot 外发仍只接受 contact/text。

## 路径与方案选择

按用户指定的窗口监听方式，采用：已登录 Telegram Desktop 频道 → 原生转发给现有 Telegram 机器人 → Bot API 接收 → Butler 归档/展开 → wxbot 投递。

可选的个人账号 API 方案不操作 Telegram 界面，但需要独立 api_id/api_hash 和登录；本机当前没有该配置，且不符合本次窗口监听要求。直接让机器人进入频道可免桌面转发，但需要频道方允许加入，不能假定对第三方频道拥有此权限。本次保留桌面路径。

不采用两套独立鼠标脚本并行运行。推荐复用 wxbot 的单一 UI 线程调度，将 Telegram 界面操作封装为可暂停状态机。采集、下载、Bot API 网络请求可以在后台运行，UI 输入由一个调度器拥有。

## Skill 与管理配置

项目 Skill 暂名 `telegram-relay`，放入现有 butler-wechat 插件。负责指导查看状态、管理已授权订阅、申请启动/暂停监听；持续监听由确定性服务完成，不由模型逐条读取、分析或重复执行转发脚本。

log 增加 Telegram 监听配置，管理员可新增、修改、停用频道。配置包括：总开关、频道名称、可取得时的频道用户名/数字 ID、Telegram 监听窗口、目标机器人用户名/ID、轮询间隔、文字/图片开关、首次历史处理方式、来源与时间头及失败处理策略。不擅自开启真实路由。

实施默认采用本机现有 Token 对应的单个机器人。配置的机器人用户名/ID用于和 getMe 返回身份核对，不能只改用户名就转给没有对应接收凭据的其他机器人。本次不引入多机器人账号管理。

窗口绑定同时核对 Telegram 程序、当前聊天标题及可获得的来源标识；名称不是唯一身份。同名窗口/频道或无法验证机器人目标时停止对应任务。Bot Token 复用现有本机配置，不写入 Skill、提示词或浏览器响应。

Skill 工具必须经过服务端签发的身份和权限校验。普通会话只管理自身被授权的订阅；全局监听窗口、目标机器人及跨用户接收范围由 log 管理员配置。频道正文只作为待转发数据，不是配置指令或工具授权。

首版不新增普通用户按频道订阅的权限模型：普通用户沿用现有“新闻消息”分组订阅，频道列表由管理员维护，Skill 的全局管理工具也仅向管理员授权。每条来源消息展开时读取新闻分组并按微信接收人去重，重叠分组/重复姓名不能造成同一条消息重复投递；实际发送前再次检查是否仍订阅。不同频道的不同源消息保留各自来源，不凭正文相同自动合并。

## 桌面操作协调

- 同时最多一个 Telegram 转发或微信发送事务；不得在微信半条输入、提及选择、图片预览或气泡确认过程中切换去 Telegram。
- Telegram 转发完成本机提交/核对后释放桌面使用权，不占用桌面等待 Bot API、网络下载或 Butler。
- 调度在安全事务边界轮转，保障微信回复及时性，也给待转发频道机会，避免单个频道刷屏导致其他任务饿死。
- 鼠标、键盘、剪贴板均属于同一事务；前后台窗口、聊天对象和草稿每阶段重新核对。用户手工切换窗口或输入时暂停任务，不与用户争抢。
- 运行期由 wxbot 主进程/单一实例锁持有桌面调度权，其他进程提交业务任务，不直接调用输入操作。网络线程不持有桌面操作权。

## 多频道与积压

每个频道独立扫描游标、消息基线、待转发任务与失败状态。消息发现后先持久化，再安排原生转发。优先用来源频道标识与消息 ID/原文链接去重；界面不能取得可靠定位或恢复依据时，记录待核对，不仅凭相同正文推断同一条消息。

首次启用默认建立基线，仅转发后续新消息。频道内部按源消息顺序处理，多频道轮流领取任务；一个频道失败不冻结其他频道。配置改变不重置游标或触发历史重发。

Telegram 端原生提交、机器人实际收件、Butler 落盘、图片就绪、微信各分段/图片确认分别记录，不能把某一段成功当成整条链路完成。跨阶段尽量以 forward_origin 与源消息标识关联；缺少可靠关联时显示独立阶段，不按同文强行合并。

消息结果不确定时不自动重复转发或重复发送，保留核对任务；确认尚未提交的失败才允许有上限的重试。log 提供队列长度、最近扫描、逐频道状态和人工处置入口。

## 内容与图片

消息头保留可获得的频道来源、原发布时间和原消息链接。正文保留文本和图片说明；显式 URL 以及 Bot API entities/caption_entities 中的隐藏链接作为链接提取，不能从截图猜测完整 URL。微信端按文字链接投递，不承诺复刻 Telegram 预览卡片或排版。

Telegram 到机器人的图片使用客户端原生转发；受保护而禁止转发的内容记录跳过，不通过截图或下载变相绕过。Bot API 的 photo/document 元数据用于下载实际图片；按文件标识、大小和类型校验，缓存到专用数据目录，下载链接中的 Token 不进入日志。

如需继续发送到微信：扩展 Butler/wxbot 附件协议，使用服务端生成的 media_id，而非接受模型给出的任意磁盘路径。微信投递队列支持文字和图片子任务，整条图文消息按一个业务包编排；同一接收人不能在该包中间混入另一频道的图片。仅确认自己的新图片气泡后将该子任务标为已发送。

同一 Bot API media_group_id 的图集通过有上限的聚合窗口合并；按来源消息顺序保存图片和说明，纯图片也建立任务。聚合超时、迟到图片、图片下载失败分别记录，不把缺图的消息标为完整成功。图片失败默认保留待处理，其他频道继续；可另配置只发文字并明确缺图提示。

服务端 Bot API getFile 当前下载上限为 20 MB；更大图片/图片文件标记不支持或待人工处理，不静默丢弃。首版图片格式、单图大小和图集数量设明确上限；视频、音频及普通文件保留元数据并显示暂不支持，不自动伪装为图片发送。

## 图片范围确认

用户已明确选择“图片也继续转发到微信”。本次包含附件下载、图集合并、Butler/wxbot 附件协议和微信图片发送，不以仅收到图片元数据或仅发送图片链接作为完成。

## 建造前复核

已由独立工程师复核设计。提出的单/多机器人凭据范围、个人订阅与新闻分组关系，已按本次复用既有机器人及新闻分组的范围在上文明确，属于实现默认，并非用户另行提出的新需求。图片终点已经用户确认；真实客户端控件和来源定位作为实施前的技术验证任务处理。

## 验证与边界

先用假 Telegram 客户端、假 UI、假网络与临时数据库验证：两应用操作绝不重叠、多频道顺序与公平性、重复/中断恢复、图集关联、附件权限和发送结果不确定时不重放。

Telegram Desktop 的真实控件、转发菜单、来源定位和图片发送方式需要本机只读检查。真实转发和微信发送另需用户明确授权；不自动重启现有服务，不触碰登录凭据或复制其他安装数据。

设计获确认后才编制实施计划和修改产品代码。该文档不代表上述能力已经上线。
