# 完整回复分句与微信收发调度

状态：用户已确认并实施；200 项离线测试及最终独立审查通过。服务由用户自行重启生效，未验证真实微信发送。

## 目标与边界

- Hermes 仍完整生成一轮回复。Butler 整理最终正文后分句，一次返回全部分句。
- wxbot 的界面操作串行：一次收件采集或一次完整句子的键入、回车及确认。等待模型不占用微信界面。
- 不同用户的请求可以并发等待，同一会话不并发开始两轮处理。默认最多 2 个模型请求，超过上限继续留在持久化就绪队列。
- 私聊、群聊 @过滤、角色与 Skill 白名单、3 秒安静合并/10 秒上限保留。群聊仍按整个群会话保持上下文顺序，成员消息不混合成一段。
- 闲时只读检查，不主动激活/滚动；保留 Unicode 键盘输入、5 字/0.5 秒、输入校验和新增自己的气泡确认。
- 本阶段不接入 Hermes 流式输出，不自动重试结果不确定的模型或发送任务，不自动重启任何服务，不提交 Git。

## 收件与发送时序

1. 发现 A 未读，登记待采集任务；界面空闲时打开 A，读取消息、事务落库并完成本次采集。
2. A 的连续消息合并就绪后，由后台任务提交 Butler。A 标记“等待模型回复”，主线程继续处理界面事件。
3. B 未读时，完成 B 的采集并入库；有并发额度即提交 Butler，无额度则保留等待状态。
4. A 回复到达期间若正在采集 B，先完成 B 的落库，再安排发件。不会把半次采集丢下。
5. 输入 A 的某句话时不能切走；期间登记其他未读，读取当前聊天。该句回车、确认完成后才释放界面。
6. 每完成一项界面任务重新调度：收件和发件都积压时交替服务，防止持续收件饿死回复或多句回复饿死收件。

“同步按顺序”指界面操作串行，不是让网络请求阻塞主线程。默认 2 个后台任务仅接触普通数据和网络，不传递 UIA 控件。

## 分句归属与规则

Hermes 保持角色化生成；Butler 在剥离行动标记、执行行动、合并补发并得到最终 `reply` 后分句；wxbot 负责投递。

- 以 `。？！!?` 和段落换行作为边界，保留原标点。
- 连续终止标点视为同一个句尾，句末右引号等收束符号留在原句，不生成只有标点的消息。
- 不按逗号或英文 `.` 拆分，避免误拆网址、小数、缩写。
- URL、行内代码和代码块中的终止字符不作为分句边界。
- 空白分句忽略；没有终止标点的剩余正文仍作为最后一句；静默回复返回零句。
- 分句仅改变投递边界，不改写正文内容，不再次调用模型。

## Butler 返回格式与兼容

保留原 `reply`、`actions`、`meta`，新增 `reply_parts`。wxbot 使用其批次 ID 作为 `msg_id` 提交，Butler 在 `meta.msg_id` 回显。

```json
{
  "reply": "你好。今天过得怎么样？有事可以跟我说。",
  "reply_parts": ["你好。", "今天过得怎么样？", "有事可以跟我说。"],
  "actions": [],
  "meta": {"msg_id": "请求批次ID", "reply_complete": true}
}
```

- 一次 HTTP 响应即包含所有分句，`reply_complete=true` 表示这轮不会再出现迟到分句，分句总数由数组长度确定。
- wxbot 一次事务保存全部分句及总数。每句持久化 `batch_id`、`seq`、稳定 `part_id`，以 `(batch_id, seq)` 防重复。
- 物理字段映射：保留旧 outbox 的全局 `seq`，上述句内 `seq` 存为 `part_seq`；`part_id` 使用既有 `id` 字段，旧 ID 保持不变。
- 老客户端继续使用 `reply`；新客户端遇到老 Butler 缺少 `reply_parts` 时，将 `reply` 当作单条回复。非 Butler 后端和本地命令保留原字符串语义。
- 新字段格式损坏时记录协议异常并使用可用的完整 `reply` 单条回退，不猜测或发出半份数组。
- 原独立窗口模式继续使用完整 `reply`，不强行接入新的多句调度。

## 按会话轮流发送

- 每次只从某个会话领取最早未发的一句。发完并确认后，该会话排到其他有就绪回复的会话之后。
- A 有 A1/A2/A3，B 有 B1/B2 时，B 已就绪即可形成 A1 → B1 → A2 → B2 → A3。
- B 尚未就绪时不空等 B，A 可以继续；B 之后就绪，在当前一句完成后获得服务。
- 最近服务顺序持久化，重启不将已经发送的句子重新插队或重复发送。
- 每个分句单独保存 pending/sending/confirming/sent/blocked/uncertain/skipped 状态、确认锚点和实际输入正文。
- A 只有全部分句 sent/skipped 后才完成本批次并解除等待标记。A 新收到的消息继续收集，等本轮结束后开始下一批。
- 一句 blocked/uncertain 会暂停该会话后面的句子与批次，其他会话继续；人工重试只处理指定异常句，不重跑模型或重发已确认句。

## 并发与身份边界

- wxbot 使用有界后台并发，同会话最多一个有效模型批次；会话请求状态、发件顺序均由 SQLite 事务约束。
- Butler 对同一有效身份/会话的处理与重置串行，避免不同窗口映射到同一个 Hermes 会话时历史交错；不同身份可以并发等待。
- Profile 级补发 `take + claim` 使用短锁整体保护，不能持有该锁等待模型。
- 补发必须核对收件身份；无收件身份的旧记录仅在 Profile 明确且唯一属于当前用户时沿用旧逻辑。多人共享 Profile 的无法归属旧记录保留并留日志，不猜收件人。
- 不改变 Hermes 的角色、白名单或群成员协议。是否实际并行生成还取决于 Hermes 运行时，本方案保证 wxbot 不因等待 A 而阻止 B 提交。

## 数据迁移、恢复和可见状态

- 将当前 outbox 的“一个 batch 只对应一个发件”约束迁移为“一批多句”；旧记录保留原 ID、状态、正文、快照、实际输入、错误及时间，映射为第 1 句，不重新分句旧的待发记录。
- 迁移是单事务，失败完整回滚；只能在用户停掉旧版 wxbot 后首次启动新版本执行，防止旧进程按单句逻辑提前完成多句批次。
- 已开始模型请求在进程中断后仍为 uncertain；未开始请求继续等待。恢复不重新请求已保存完整分句的模型结果。
- 已发句子不重放；中断发件按每句的确认锚点和实际输入只读核对。人工 sent/skip/retry 后重新计算整批状态，不能只完成其中一句就结束整轮。
- 日志与队列查询显示：待提交、等待模型、回复已就绪、分句序号/总数、发送确认、整轮结束及异常原因。

## 验收场景

- A 模型阻塞时 B 可采集并提交；同一会话的两轮不会并发。
- 正在采集 B 时 A 回复到达，B 完成落库后再切 A；正在打字时不切换。
- A 三句/B 两句交错发送，用户内部顺序不变；B 后到时能在当前一句完成后获得服务。
- 回车前新收到的用户消息先入库，确认锚点刷新不会吞消息；闲时无选择/激活/滚动操作。
- 分句保留连续标点、右引号与末尾正文；网址、小数、代码不误拆，行动标记不泄漏。
- 全部句子保存成功后才进入发件；其中一句异常不结束整批，也不挡住其他用户。
- 同 Profile 的并发补发不会重复认领；无法归属的历史补发不跨用户投递。
- 旧库迁移保留所有任务与确认信息；逐句恢复、跳过、重试均不重复已确认分句。
- 全部验证采用离线假 UI、假模型和本地测试 HTTP，不发送真实微信测试消息。

交付后需用户自行重启 wxbot 与 Butler；Hermes 无需为本功能重启。
