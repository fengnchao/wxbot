# 微信图片理解与语音转文字接入方案

日期：2026-10-27。状态：方案草案，已完成独立只读设计审阅，待用户审阅；尚未实施，微信本机控件兼容性待验证。

## 已确定的要求与本方案的默认选择

用户已选择：语音直接读取微信自带“转文字”的结果，不新增云端语音识别接口。本次交付为图片、语音识别的接入方案。

本方案提出的默认选择：图片使用当前已有的 Codex 后端理解；在 wxbot 主窗口模式先上线，文字回复继续使用现有队列、身份、角色、记忆和群聊策略。图片仍会发送给当前配置的 Codex 模型。“不用云端”在本方案中指不另接语音识别 API，不等于整套机器人离线运行；微信自身转文字的实现和联网行为由微信决定。

第一版支持静态图片、单条语音消息及与其连续发送的文字；回复形式为现有文字回复。视频、通话、音频文件附件、动画表情、语音回复、跨批次自动追溯图片不在第一版范围。

## 当前代码与影响范围

- `wxbot/wechat/chat_window.py`：`Message` 仅有文字与发送方信息；`_read_entries()` 虽枚举非文字条目，`read_messages()`、`read_bundle()` 等仍过滤非文字消息。
- `wxbot/state.py`：仅按正文重叠判断新增消息。修改正文来容纳语音转写会破坏现有去重；连续两个 `[图片]` 也无法代表不同消息。
- `wxbot/inbox.py`：单个 UI 线程负责收件、发送和 Telegram 窗口任务；新的右键菜单、图片复制、转写读取必须加入同一调度。
- `wxbot/queue_store.py`、`queue_schema.py`、`queue_worker.py`：收件和合并批次以文字为中心，当前没有媒体准备状态。
- `wxbot/processor/router.py`、`processor/butler.py`、`butler/server.py`、`core.py`：当前调用链主要传 `text`，需要向后兼容地增加有序内容项。
- `butler/media.py` 和 `/v1/media`：已有图片校验、缓存与上传能力，但现有缓存元数据没有入站消息归属，不能仅凭知道一个 `media_id` 就让任意会话使用。
- `butler/backends/codex.py`：目前组装 `TextInput` 和 `SkillInput`；本机固定版本 `openai-codex==0.163.0` 已提供 `LocalImageInput`。
- `butler/group_context.py`：目前只接受文字归档；需让媒体就绪后再归档，避免同一来源先存占位文字、后改成转写文字而产生冲突。

## 方案与取舍

| 能力 | 采用方案 | 原因及代价 |
|---|---|---|
| 语音 | 微信原生转文字，读取对应语音条目的转写区域 | 用户已选；无需接入额外识别服务，依赖当前微信控件是否可读 |
| 图片 | 通过微信图片菜单复制图片，校验后作为 Codex 图片输入 | 复用现有后端，可同时处理照片内容和图中文字；需要新增可靠的图片获取步骤 |
| 媒体调度 | 持久化任务＋现有 UI 线程中的分步状态机 | 与发送、Telegram 任务共用界面时不会同时抢焦点 |

语音不采用原始缓存提取、播放内录或另接 ASR。图片曾考虑仅做 OCR 或直接截聊天缩略图：前者不能覆盖照片理解，后者容易丢失细节，因此第一版不作为默认路径。复制拿不到完整图片时先标记失败，不把缩略图当原图提交。

## 预期使用行为

私聊收到语音，机器人先取得微信转写文字，再像收到一条文字消息一样理解并回复。不会下载语音文件，也不播放语音。

私聊收到图片，机器人取得图片；用户在现有合并时间内接着发“帮我看看这是什么”，则图片和文字按顺序进入同一轮。只有图片时，使用简短的默认提示，请模型理解图片并结合当前对话自然回应。

群聊沿用当前是否直接请求、概率回复、静默或表情的策略，不因收到媒体一律调用模型。语音先转写，再参与现有群聊判定；转写文本不产生“已核验的微信 @”证据。图片与同一成员在同一合并窗口内发送的文字可合并，其他成员发言或命令形成边界。

静默群语音以转写文字归档；静默群图片只归档“收到图片”的来源信息，不调用 Codex 分析。第一版仅提交当前批次图片，后续批次单独问“刚才那张图”不承诺自动补图。图片理解失败时明确说明无法读取，不用占位文本让模型猜图。

## 总体流程

```text
微信消息条目
  → 判断类型、会话和发送方
  → 原始消息与媒体任务原子入队
  → UI 线程完成媒体准备
       ├─ voice：定位语音 → 已有转写/点击转文字 → 读取绑定结果
       └─ image：定位图片 → 复制图片 → 校验并写本地暂存
  → 后台将图片上传本机 Butler，取得绑定来源的 media_id
  → 媒体就绪后按原接收顺序合并批次
  → Butler 解析身份、校验内容归属
  → Codex 接收文字与图片 → 原有文字发件队列
```

语音转写在微信界面完成；Butler 不接收音频。图片上传地址为本机 Butler，之后由现有 Codex 后端提交图片输入。

## 一、先验证微信控件契约

正式实现前用现有脱敏 `tools/probe.py` 及受控样本确认下列信息，不预先编造 `ClassName`、`AutomationId` 或菜单坐标：

1. 语音和图片条目的类型、可见范围、发送方识别、会话及条目锚点。
2. 右键语音后出现的菜单是否归属于当前微信窗口，“转文字”菜单项如何定位。
3. 转写完成、处理中、失败、已有转写分别如何表达；转写内容能否通过 UIA 的名称、文本或 Value/Text Pattern 读取。
4. 转写区域属于哪个语音条目；界面上同时有多条语音时也能一一对应。
5. 图片“复制”是否提供可解码的图片数据、尺寸是否足够，是否需要先进入图片查看器；下载未完成、撤回、过期如何表现。

如果语音文字没有可读取的 UIA 表达，第一版报告该微信版本暂不兼容，不自动改用录音、外部 ASR 或 OCR。若图片复制路径不能确认来源与内容，图片能力暂不启用。两项分别校准和启用，一项失败不阻止另一项及原有文字聊天。

## 二、语音转写状态机

新增 `wxbot/wechat/voice.py`，只负责微信 UI。流程为：

1. 核对前台 HWND、会话类型、消息锚点和发送方。
2. 已有成功转写则直接读取；否则右键目标语音，仅从本次新出现、归属已核对窗口的菜单选择“转文字”。
3. 关闭菜单并核对界面恢复。轮询该条语音下的转写区域，不能读取整屏最后一段文字来猜结果。
4. 明确完成，或没有处理中状态且两次间隔采样读取到相同非空结果时，保存转写。错误提示和按钮名称不能作为正文。
5. 转写写回原 `source_id`，更新媒体状态，不追加一条新的收件消息。

建议初始默认：单次等待 20 秒，最多 2 次尝试。已点击转文字后超时，下一次先只读检查原条目，只有确认尚无处理结果且菜单操作可安全重复时才再次请求转写；无法重定位则转人工核对。具体轮询间隔由实现者根据样本确定。

等待使用单调时钟和分步 `step()`，不在 UI 线程长时间 `sleep()`。菜单清理并确认界面恢复后可释放 UI 调度权；再次查看结果要重新核对目标，不能继续使用旧坐标。

## 三、图片获取与模型输入

新增 `wxbot/wechat/image_capture.py`，与已有负责发图片的 `image.py` 分开：

1. 核对目标图片和会话，优先使用经校准的原生“复制图片”路径；如需打开查看器，也必须核验该查看器属于当前微信窗口及所选消息。
2. 复制前保存可安全恢复的剪贴板格式与版本，操作后只读取本次复制产生的图片。目标窗口、剪贴板版本或用户操作变化时放弃本次采样，不能读取旧图片当成新收件。
3. 将有效数据标准化为静态 PNG/JPEG/WebP，校验解码、文件大小、像素、帧数与哈希。上限沿用 `MediaStore` 的 20 MiB、4000 万像素，单批最多 4 张。
4. 原子写入 wxbot 本地暂存并关联 `source_id`；网络上传和重试在后台执行，不占用 UI 线程。剪贴板恢复遵循现有“用户后续复制的内容优先保留”原则。
5. Butler 取得图片后在对应隔离 worker 的只读工作区内暂存验证后的副本，组装 `TextInput` 与 `LocalImageInput`，保持文字、图片顺序。

单批超过 4 张时保留各原始记录，按现有成员和命令边界拆成多个有序批次，每批最多 4 张；不静默丢掉第 5 张。无法复制、图片未加载、损坏或过期时不自动改用整屏截图。

继续关闭 shell、浏览器、原生 `view_image` 等工具。图片通过 turn 输入传入，不向模型开放任意路径。需单独验证 `LocalImageInput` 在当前隔离配置和所选模型下可用；不兼容时明确报告，不扩大整个磁盘读取权限。

## 四、消息身份、队列与去重

新增的入站记录至少包含：

| 字段 | 含义 |
|---|---|
| `source_id` | wxbot 初次确认采集后生成并持久化的消息来源 ID |
| `kind` | `text`、`voice`、`image` 或不支持的消息类型 |
| `match_key` / `locator_evidence` | 与消息显示内容分离的匹配证据、局部顺序和 UI 定位线索 |
| `raw_text` / `resolved_text` | 原始可见文字与语音转写；转写不覆盖去重依据 |
| `content_state` | `pending`、`working`、`ready`、`failed`、`needs_review` |
| `media_id` / `local_file_id` | Butler 媒体引用及本机受控暂存标识 |
| `attempts`、`next_attempt_at`、`error_code` | 有界重试与可观察的失败原因 |

媒体任务单独存表，按 `source_id` 唯一关联收件记录；消息、快照和初始任务在同一事务提交。文件系统写入采用临时文件＋原子改名，数据库提交失败留下的未引用文件由清理器回收。上传成功但本地确认前崩溃，用相同来源和哈希向 Butler 重试获取同一媒体引用。

UI Runtime ID 只在当前已验证控件生命周期内作为定位证据，不作为可跨重启的永久消息 ID；不能用坐标、头像、`[图片]` 占位符或图片哈希单独判断消息唯一性。相同图片连续发两次属于两条消息，内容哈希仅用于字节校验和可选缓存复用。

匹配采用消息类型、原始稳定特征、邻接锚点和重复项相对顺序。语音结果展开时，将产生的派生转写节点归到原语音，排除在“新文字消息”扫描之外；刷新布局不能生成第二条任务。媒体快照失去重叠或多个候选不可区分时停止推断并记录待核对，不沿用文字流程“取最后一条”的兜底。纯 UIA 缺少永久消息 ID 时，不承诺对任意历史滚动和丢失锚点都能做到无损自动恢复。

合并计时保持现有安静 3 秒、最长 10 秒的原始收件窗口；媒体准备时间另计，转写完成时间不改写 `received_at`。同一会话最早媒体未就绪时，后续批次不能越过；其他会话可以继续处理。到达超时或尝试上限后转终态，让后续消息继续。

启动恢复区分未提交收件与已生成的回复：持久化的未完成媒体收件保留，能够重新确认锚点时才继续；中断时已点击转文字的任务先只读核对结果，图片已上传则直接复用引用，失去锚点则转 `needs_review`。现有 `queue.restart_chat_policy` 主要控制旧回复的续发，不把其 `discard` 含义扩大为删除未处理收件。已提交模型但结果未知沿用现有 `uncertain` 处理，不自动重放。旧文字快照只用于文字对齐，不因升级回收历史媒体。

## 五、Butler 接口、归属与兼容

入站图片使用新增的鉴权接口 `POST /v1/inbound-media`：multipart 中包含图片字节和元数据 `source_id/contact/channel_type/member_key/avatar`，不接受调用方指定本地路径或外部 URL。服务按现有通道身份解析规则确定归属，不允许模型提供 user_id/owner 来改变身份。

现有 `/v1/media` 和外发媒体能力保持原用途，不把“可读取某个缓存文件”当作入站授权。新建入站绑定记录，以服务解析的会话/成员作用域和 `source_id` 唯一约束；同一来源、同一哈希幂等，同一来源换内容返回冲突。`/v1/handle` 再次核验媒体属于本次会话、来源及身份作用域。

`/v1/handle` 保留旧 `text` 字段，增加可选的有序 `content_items`，例如：

```json
[
  {"kind": "image", "source_id": "source-1", "media_id": "server-issued-id"},
  {"kind": "text", "source_id": "source-2", "origin": "wechat_text", "text": "帮我看看这个"},
  {"kind": "text", "source_id": "source-3", "origin": "wechat_voice", "text": "重点看右上角"}
]
```

存在内容项时，服务端验证顺序、数量、类型和归属，并从内容项生成供日志和检索使用的文字，避免 `text` 与内容项冲突。只有旧 `text` 的请求继续原行为。语音来源字段只用于追踪，不提升权限；转写内容默认作为普通对话，不自动执行 `/reset` 等本地管理命令。

向 Processor、Router、Butler core 和共享后端接口逐层增加可选内容项；纯文字调用不强制给旧适配器新增参数。Codex 实现图片能力，其他后端遇到图片时明确返回能力不支持，不能只把 `[图片]` 当正常已识别消息。

群归档在媒体就绪或终态后一次完成：语音存最终转写或明确失败事实，图片存来源类型和占位说明。通过批次来源 ID 幂等归档，不回写已经冻结的群上下文快照，不把图片内容提升为跨成员私有记忆。图片或转写中的内容不能改变服务签发的工具身份和权限。

## 六、调度、失败行为与管理台

扩展 `MainInbox.tick()` 的现有调度，让采集、媒体 UI 步骤、文字/图片发送及 Telegram 任务公平轮转。任一菜单或查看器未安全关闭时，其他占用微信界面的任务不得启动。纯后台上传或等转写期间，确认 UI 干净后可调度其他任务。

界面恢复失败、前台被人工切走、会话变化或草稿冲突时停止点击；可安全清理仅清理本任务创建的菜单/查看器，不触碰用户草稿。不能恢复到已知状态则 `needs_review`，沿用现有 UI 审核阻断方式。

普通识别失败只结束对应媒体任务，不让其无限占住模型槽位。需要回复的批次：全部内容不可用时返回一次简短提示，例如“这条语音没转出来，麻烦发文字”；部分可用则处理可用内容，同时明确缺失项，不猜未读取内容。静默群批次只记失败，不新增打扰。技术重试使用原任务 ID，不能造成第二次回复。

log 复用消息流转和队列页面，增加类型、媒体准备状态、耗时、尝试次数、错误原因与媒体来源信息。语音转写与原消息在同一条详情显示；图片详情按现有管理台鉴权提供可选预览。普通流转事件不携带整图/base64/音频或凭据，不增加新的常驻服务。

## 七、配置与保留策略

新增无凭据模板配置（名称为本方案提案）：

```toml
[recognition]
enabled = false                   # 校准并验证后再开启

[recognition.voice]
enabled = true
provider = "wechat"
timeout_seconds = 20
max_attempts = 2

[recognition.image]
enabled = true
provider = "codex"
timeout_seconds = 15              # 一次 UI 获取步骤的总等待预算
max_attempts = 2
max_images_per_batch = 4
cache_retention_days = 7
```

语音、图片及菜单选择器放在 `wechat` 对应配置表中，通过探针填写，不写未经验证的硬编码控件名。log 的 schema、编辑器、配置视图需要一并支持校验和展示。仅支持主窗口模式启用识别；独立窗口配置启用时给出明确不支持提示，文字路径照常工作。

wxbot 暂存和 Butler 已接收的入站图片均默认保留 7 天，只删除无活跃收件、重试、模型或发件引用的文件；已成功上传且没有本地后续用途的 wxbot 暂存可提前回收。入站清理不得误删现有 Telegram/外发图片，绑定元数据与字节引用分开管理。失败日志保留按项目现有日志策略，运行图片和配置均不入 Git。

## 八、落地顺序与验收

1. **控件可行性验证**：用受控的现有语音/图片样本校准菜单和读取结果，先确认两条 UI 路径确实可用；本阶段不自动发送测试消息。
2. **收件模型与队列**：支持媒体类型、来源 ID、持久化任务、派生转写节点识别、新旧快照及数据库迁移；保持文字回归通过。
3. **语音闭环**：完成微信转文字、去重、顺序合并、失败提示和群归档；不引入音频依赖。
4. **图片闭环**：完成图片复制、本机上传、来源绑定、worker 工作区准备及 Codex 图文输入。
5. **管理台与兼容性**：显示状态和失败原因，补配置模板、清理和使用说明，再进行受控真实验收。

离线验证使用临时数据库、图片、假 UI、假剪贴板和假投递。重点覆盖：

- 同时收到两条同样时长语音、两张相同图片，也不会吞掉后者；展开转写不会重复入队。
- 转写超时、菜单缺失、结果挂错条目、撤回和重启不会导致猜内容或重复回复。
- 图片与同成员文字正确合并，跨成员/命令不混批；媒体等待不让同会话后续消息超车。
- 模型不会拿到别的会话的 media_id、任意磁盘路径、未完成图片或无效格式。
- 媒体任务与现有发送、真正 @、Telegram 任务不会同时操作界面；用户草稿与新剪贴板内容保留。
- 纯文字、静默群、身份/记忆隔离、旧接口和旧配置回归；数据库迁移失败前有现有机制的备份。

真实验收使用明确的测试聊天和无敏感样本；项目要求真实微信测试发送必须另有用户明确授权，不自动重启已有服务。Codex 图片兼容性可先用临时自制图片、临时业务目录和假投递验证，真实界面与模型额度验证的结果分别记录。

验收目标：支持的可见新消息可识别，语音一条消息只产生一个转写来源，图片和文字按顺序进入同一轮；故障可见、重试有界、旧文字聊天正常。控件探测通过不等于真实收发已验收，必须分别记录。
