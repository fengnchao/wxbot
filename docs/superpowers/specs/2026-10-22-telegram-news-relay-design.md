# Telegram 联合早报文字转发到新闻分组

状态：用户于 2026-10-22 审阅后回复“可以 开发把”，已批准设计并要求开发。

## 已确认的目标

- 使用安装者自己的 Telegram 账号接收消息；用户是普通成员，不依赖向来源添加机器人。
- 来源为用户确认的官方频道 `@zaobaosg`，显示名为“zaobao.sg 早报”。
- 只接收文字，按原文推送给 log 用户分组中“新闻消息”当前绑定的微信用户。
- 首次启用从最新消息开始，之后记录消息 ID、断线补收、去重，并保存逐人逐段的投递回执。
- 用户已同意先编写本设计；实现和执行方法在设计审阅后的实施计划中确认。

## 方案与范围

采用 Telethon 的个人账号客户端接口，新增独立运行的 `butler.telegram` 接收服务。该服务属于 Butler 业务层；wxbot 继续独占微信界面操作和既有发送队列。

不采用桌面窗口采集：直接接收结构化消息可以保留稳定的频道 ID 和消息 ID，避免依赖窗口前台状态或 OCR。公开网页轮询可以免账号登录，但需要解析网页、处理分页及更新边界，不作为本次实现方式。

文字包括独立文本消息和图片、视频附带的说明文字；媒体本体不下载、不转发、不做 OCR。仅含媒体而没有文字的消息记录为忽略。频道消息没有发言人时只展示频道来源，不伪造个人发言人。

转发保留正文、发布时间、来源名和 Telegram 原消息链接。使用北京时间展示，底层时间保存为带时区的时间。正文不经过模型改写，群消息中的指令仅作为转发内容。

本次为持续接收后尽快逐条投递，不并入每日 09:00 RSS 简报。RSS 的类别、来源及每日条数仍只控制现有每日早报；Telegram 只复用新闻接收人分组，不套用 RSS 的每日条数限制。

第一版不接收编辑/删除事件，不发送 Telegram 回复，不主动加入频道，不补发首次启用前的历史，不增加 log 配置页面或管理按钮。

## 组件与调用方向

```text
Telegram 账号授权会话
  → 指定来源的新增消息通知 / 断线恢复扫描
  → Butler Telegram 收件记录及游标
  → 读取新闻分组，生成逐人逐段任务
  → Butler 现有 POST /v1/push
  → wxbot 现有发送队列及微信确认
  → Butler Telegram 投递回执
```

- 接收适配器仅负责连接 Telegram、核对账号和来源、获取结构化消息。
- 收件存储负责扫描游标、原文、接收时间和唯一性约束。
- 转发服务负责分组读取、消息格式、分段、收件人快照及发送状态；业务逻辑留在 Butler 包。
- HTTP 客户端复用现有逐人推送契约：`type=1`、`messageType=1`、明确的 `contact`。不调用 `/v1/handle`，避免将新闻当作对话请求执行。
- 不直接打开或写入 wxbot 的 SQLite 队列，不启动第二个微信 UI 实例。

使用逐人请求而非一次群发请求，是为了逐人保存确认状态，避免部分成功后重复发送整组。新闻分组仍由现有配置决定，并非复制固定联系人。

## 配置和本地授权

新增独立的 `config.telegram.example.toml` 凭据空白模板及本机 `config.telegram.toml`，由专用配置加载器读取；不把新配置注入现有 Butler 常驻进程。

配置包含：是否启用、来源列表、安装者申请的 `api_id`/`api_hash`、会话及状态路径，以及可选代理连接参数。默认关闭；示例来源为 `@zaobaosg`。代理由 Telegram 接收器单独配置，不将代理发送给本地 Butler HTTP 请求。

已实现的命令：

- `python -m butler.telegram login`：仅做本机交互授权，不发送微信消息。
- `python -m butler.telegram run`：显式启用已授权的接收与转发服务。
- `python -m butler.telegram status`：只读展示账号/来源是否已绑定、连接状态、积压及投递结果。

命令支持显式 Telegram 配置与 Butler 配置路径；相对路径以对应配置文件所在目录解析。不得依赖调用者当前目录。

首次授权需要安装者自行申请 Telegram API 参数，并在本机交互输入登录验证码及必要的二次验证信息；不得通过聊天或命令参数传递验证码、密码及会话内容。不读取或复用桌面客户端的 `tdata`。

运行时校验配置、会话是否已授权、账号 ID 和来源 ID。首次解析用户名后绑定稳定数字 ID；后续若用户名指向不同 ID 或会话账号变化，则停止并报告，不自动切换来源或账号。来源必须是配置允许的已加入频道/群；无权访问时明确失败。

Butler 配置仍使用现有解析器；在内存中使用服务认证，不打印配置对象、认证字段或原始异常响应。配置错误不能回退到默认账号、默认来源或其他联系人。

本机配置、会话及数据库位于被 Git 排除的位置；补充 `config.telegram.toml`、`*.session` 及相应辅助文件的排除规则。示例和日志不包含真实密钥。

## 首次启动、扫描和游标

1. 获取单实例锁，确认本地授权和来源身份。
2. 新来源第一次启用时读取该频道最新消息 ID，事务保存为起始边界；该 ID 及之前的消息不转发。空频道以零为边界。
3. 启动期间已收到的事件只用作扫描通知，不直接推进游标；完成起始边界初始化后扫描更大的消息 ID。
4. 之后按 ID 从旧到新分页读取边界之后的消息；每页消息入库与扫描游标推进在同一事务提交。
5. 消息事件、连接恢复和定期间隔都可唤醒同一串行扫描器。重复扫描依靠唯一约束消除；事件先到后到不改变处理顺序。
6. 已存在边界的来源在重启后继续扫描边界之后的消息，补收离线期间的新内容，不重新初始化为“现在”。

游标表示“已经安全扫描并落库的位置”，不表示“已发送到微信的位置”。发送慢或结果不确定不阻塞接收；收件数据库写入失败时不推进游标。

Telegram 网络错误使用有界退避；遇到服务端限流按其等待时间恢复。授权撤销、账号不符和来源身份变化停止接收并记录原因。存储失败停止扫描，不静默丢弃。

## 新闻分组与投递

- 从传入的 Butler 配置解析 `group_file_path()`，使用与 log 相同的分组文件，读取 `groups["1"]`。联系人去空并按名称去重。
- 分组缺失、不可读或格式损坏时记录错误，暂停相关任务，禁止回退到其他联系人。
- 每条消息首次展开任务时读取最新分组，并原子保存收件人快照及全部分段；新增订阅者从后续展开的消息开始接收，不回补旧消息。
- 新闻分组为空时将该消息记为“无订阅者跳过”，不发送；之后增加联系人不重放该消息。
- 每次实际发送前再次确认收件人仍在新闻分组。已移除的人，其未提交部分记为取消；已发送或结果不确定的部分保留原状态。
- 长文本按段落/文本边界分段，以约 500 字为目标，URL 保持完整；不能在完整 URL 内截断。每段保留来源与消息标识，分段文本和顺序一次生成并保存，重启不重新改写。
- 接收任务与发送任务使用分离的执行循环；网络等待不持有数据库事务或微信 UI 对象。
- 同一接收人按来源消息和分段顺序发送。该接收人的不确定投递阻塞其后续任务，其他接收人可继续。

## 持久化、回执与恢复

状态保存在 Butler 数据目录中的专用 `telegram/` 子目录，不共用每日早报的日期标记、日报或发送数据库。

最少保存三类记录：

- 来源状态：已绑定账号 ID、来源 ID、起始边界、扫描游标、连接/扫描时间及错误类型。
- 收件：来源 ID、消息 ID、发布时间、文字、原消息链接、入库时间、展开/忽略/跳过原因。唯一键为 `(source_id, message_id)`，相同正文的不同消息仍可分别转发。
- 投递：收件记录、收件人、段序、固定正文、状态及回执时间。唯一键为 `(source_id, message_id, contact, part)`。

投递状态与处理规则：

- `pending`：尚未提交，可在后续运行继续处理。
- `sending`：先事务记录再发出 HTTP 请求；重启后遗留的此类记录转为 `uncertain`。
- `sent`：仅在 Butler 返回 `meta.ok=true` 且确认的联系人匹配时记录；永不自动重发。
- `not_submitted`：认证缺失，或明确在入队前被 Butler 拒绝。记录失败原因，不在本次运行中反复提交；后续人工处理不影响已确认记录。
- `uncertain`：超时、连接中断、无有效成功回执、未知 HTTP 失败或进程在提交中退出。保留记录，不自动重发。
- `skipped_removed`：尚未提交时收件人已退出新闻分组。

不宣称网络发送具备端到端 exactly-once。当前 `/v1/push` 没有可依赖的跨请求幂等键，遇到未知结果只保留待核对状态。本期提供只读状态及日志定位信息，不自动修改 wxbot 状态、清库或解除不确定记录；核对后的恢复操作另行明确授权。

单实例锁覆盖此接收服务的生命周期，防止同时消费同一会话和转发数据库。锁释放后才能恢复遗留提交。停止服务时停止接收和领取新任务；保留尚未完成的记录，不影响 Butler、wxbot 或 log 的现有进程。

## 可见性与错误报告

状态输出展示来源、最近扫描时间、待转发数、已确认接收人数、明确失败数、不确定数及跳过原因。每条消息可通过来源 ID、消息 ID 和收件人定位对应日志。

“已接收 Telegram 消息”“已提交 Butler”“微信发送成功”分开报告。发送成功必须有 Butler 的微信成功回执，不能用 HTTP 200、已入队或已生成文本代替。

现有 log 收发队列继续展示 Butler → wxbot 的投递；Telegram 收件状态由新服务的日志和只读命令提供。本期不承诺在旧 log 页面新增专用 Telegram 卡片。

## 代码范围和兼容性

- 新增 `butler/telegram/`：配置、Telegram 客户端适配、持久化、转发服务和命令入口；按职责拆分。
- 依赖使用可选的 Telegram 安装分组；在本项目 Python 3.14 环境验证兼容性后固定合适版本，普通微信安装不强制新增接收依赖。
- 增加凭据空白模板、使用说明及 Git 忽略项。
- 复用既有 `/v1/push` 契约；只读状态和登录命令不依赖微信发送。不改变每日 RSS 新闻模块行为。
- 如需抽取现有新闻模块的通用 HTTP 推送客户端，只抽取协议相关代码并以回归测试保证原有行为；不将每日日期防重逻辑用于 Telegram 消息。
- 不覆盖现有用户改动，不重启常驻服务，不新增自动启动、定时任务或自动入群行为。

## 验证与验收

所有自动测试使用临时目录、假的 Telegram 客户端及假的本地 Butler HTTP 回执，不连接真实账号、不读取真实会话、不接触真实剪贴板、不发送真实微信测试消息。

必要场景：

1. 首次边界前的消息不转发，初始化期间到达的新消息不丢失；空频道也能启用。
2. 事件乱序、重复通知、断线补收及重启均不重复展开任务；不同消息 ID 的相同文字不会误去重。
3. 游标与入库同事务，模拟写入失败不越过未保存消息。
4. 文字和媒体附带文字可接收；空白、无文字媒体及非允许来源被忽略。
5. 修改新闻分组后新消息读取新联系人；空组、坏配置及发送前移除联系人按规则处理。
6. 长文和网址分段保持正文顺序，逐人逐段保存；重启不重新生成已有任务。
7. 成功、明确拒绝、超时、错误回执、联系人不匹配及遗留 `sending` 均如实分类；已确认和不确定记录不重放。
8. 单个接收人阻塞不影响其他人；发送等待不阻止收件落库。
9. 双实例、未授权会话、账号更换、来源 ID 变化和服务端限流均有确定行为。
10. 配置解析、错误及状态输出不泄露密钥，示例可分发；RSS 日报原有投递行为通过相关回归验证。

离线验证通过后，部署步骤为：安装 Telegram 可选依赖、由安装者在本机保存参数并完成授权、核对解析后的来源，再显式启动接收服务。首次真实联通和投递须按用户授权范围执行并核对回执，不自动重启既有服务。
