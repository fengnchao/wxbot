# 用户身份、记忆管理、群上下文与微信真实 @ 设计

日期：2026-10-25。状态：用户已批准并完成代码实施；真实微信控件兼容性待本机验证。

同日追加确认：用户要求收到消息即自动建立用户档案，群静默归档也登记；log 保留新增、修改与绑定权限。可靠头像建立新的独立空记忆身份；仅有稳定观测 ID 时建立待核对记录，不授予个人记忆权限。启动同步旧快照身份不重放历史请求。详见后续收件修复计划。

## 用户已确定的要求

- 在 log 管理台管理人工身份绑定，列表按“头像截图、用户 ID、群名－群昵称／私聊昵称、用户记忆按钮”排列。
- 可以上传头像、填写昵称和所属群聊或私聊，生成新用户 ID，创建空白记忆空间。
- 长期记忆默认按群成员／私聊身份隔离；同一个人在不同位置的记忆，仅经管理员手工绑定才共享。用户已明确选择此方案。
- 提供记忆查询、修正、删除，并改善相关记忆召回。
- 静默群消息不再无条件调用模型；保留群聊上下文。
- 群上下文按成员隔离，同时能理解同群其他人的公开发言。
- 最新补充：真正 @ 也在本次范围内。回复必须在微信 @ 选择器中选择成员，不能用文本拼接冒充。
- 第 5 项复用现有实时工作流和消息流转日志，不另外建设重复日志系统。

## 方案与取舍

采用“固定内部用户 ID＋多个通道绑定和头像特征＋成员独立会话＋同群公开上下文”。
这是前序建议第 1 项的细化，用户已指定人工管理入口并接受身份默认隔离。

其他考虑过的方案：继续用头像哈希充当用户 ID，改动小，但换头像或采样变化会切断记忆；全群共用一个模型会话，容易保持对话连续，却难以保证个人记忆边界。本次不采用这两种方案。

固定用户 ID 用随机 UUID，不从昵称或头像哈希生成；头像哈希只是识别线索。上传同一头像不会自动合并用户。创建用户不写入“空白”占位记忆，记录数量从 0 开始。

## 当前代码约束与已知问题

- wxbot 从消息行头像截图计算 64 位差异哈希，并把该哈希传作 member_key；Butler 当前在群 uid 后追加 member_key。
- 目前上传截图产生的参考哈希与收件采样裁剪方式没有统一，参考图是 36×36，运行配置采样上限为 48×48；不能把已有参考映射标为已验证身份。
- 识别失败会生成随机 unknown 标识；这类标识不应获得可持久写入的个人记忆权限。
- 现有 Codex 记忆 owner 包含通道身份与聊天标题；需要与显示名称及头像解耦，角色变化仍可切换会话，但不应切断个人记忆。
- 当前运行时记忆视图只返回 contact，没有供管理台可靠区分同群各成员的内部用户 ID，且有全局 100 条上限。
- 静默和表情批次目前也先调用模型；本次调整触发流程。
- TypingSession 当前按纯文本精确核对草稿；真正 @ 在微信输入框中可能表现为对象占位符，不能直接沿用纯文本核对方式。

## 职责与数据归属

业务身份、绑定、头像参考和记忆管理由 Butler 服务拥有；wxbot 负责 Windows UI、实际头像采样和收发队列；log 作为管理入口转发有权限的业务操作，不自行伪造模型工具身份。

在业务数据库新增可迁移的结构：

- users：不可变 user_id、显示名称、创建时间、版本；身份记录存在即有空记忆空间。
- bindings：绑定 ID、群聊或私聊类型、会话名称、群昵称／私聊昵称、user_id、启用状态、版本。
- avatar_references：归属 binding、标准化头像图片、算法版本、一个或多个特征、人工确认信息；图片仅存本地受控路径。
- memory_scopes：绑定对应的长期记忆归属；默认独立，显式关联后可指向同一 user_id 的共享记忆。
- memory audit：记忆新增、修正、删除及绑定变更的来源和时间；删除的内容从后续模型检索中排除。
- group context：群绑定、稳定序号、消息来源／队列 ID、发言绑定／未知状态、正文、时间和机器人公开回复；唯一来源约束保证重试不重复入档。

已有队列记录保留原始观测 member_key，必要时增加解析后的 binding_id / user_id 快照。不要改写旧消息或把所有旧哈希推断成新用户。

## log 用户管理

在“用户与任务”分组新增“用户与记忆”；保留现有运行事件页面入口，并可从用户详情跳到按该身份筛选的工作流。

列表列顺序：头像、用户 ID、会话－昵称、记忆操作；同一用户的多个绑定可展开。支持按群、私聊、绑定状态和昵称查询，服务端分页。

“新增用户”填写会话类型、选择／填写群名或私聊会话名、昵称，并上传头像；保存后生成永久 ID，记忆 0 条。创建重复绑定时返回冲突，不根据相同昵称自动覆盖。

详情允许补充头像参考、改昵称、停用或重新绑定；“查看记忆”展示当前明确范围，并提供新增、编辑、删除以及修改记录。变更用版本号防止旧页面覆盖新数据。

上传仅接受可解码的 PNG/JPEG/WebP，限制文件大小和像素数，重新编码并丢弃原始元数据，不接受外部图片 URL、任意保存路径或可执行格式。默认上限由实现者以项目现有依赖确定并写入接口文档。

“手工绑定为同一用户”先展示哪些绑定及长期记忆会关联。记忆同名 key 冲突需展示两边内容供管理员决定，不能静默覆盖；一侧无记忆时可直接关联。不同绑定的角色、聊天会话和聊天历史始终分开。

## 识别和身份解析

上传参考与实际收件采用同一套可离线测试的裁剪标准化和特征算法，算法带版本。稳定 user_id 与算法版本无关。

只在当前会话绑定范围内匹配；头像特征、昵称和已有人工绑定共同作为候选证据。昵称不作为唯一身份凭证，相似度不足、多个候选接近或头像识别失败时标记“待绑定”。

相似匹配阈值必须用代表性图片测试确定，不能用任意最近邻直接认人。管理员可确认新增头像属于既有用户；不自动合并跨群、私聊身份。

未确认身份的消息可进入同群公开上下文，但不写入其他人的记忆。需要个人记忆的回复必须先有可靠绑定；识别不足在 log 明示，不用每条随机 ID 积累永久用户。

## 长期记忆

服务端基于已确认绑定解析 memory owner；模型工具只读写本次服务签发的 owner，不接受模型自行指定用户或记忆范围。

每轮生成回复时，在当前允许范围内提供有长度预算的相关记忆片段。记录 key、来源绑定、创建／更新时间和管理修改历史；不把整个数据库注入模型。

保留“仅保存用户明确要求记住的事实／偏好”规则。支持“记住”“查询”“更正”“忘掉”的授权工具及 log 管理操作。删除后不再召回，并使持有旧值的相关会话失效或切换上下文版本，避免旧会话持续复述已删除内容。

同一人跨通道共享长期记忆只由人工绑定建立。群聊回复只能读取该群绑定有权访问的记忆；管理员关联私聊记忆前明确展示群聊将能使用的范围。不向同群其他成员的请求暴露该用户私有记忆。

旧 memory owner 通过明确的旧身份到新绑定关系迁移。默认保留原始数据和迁移审计，不按昵称猜测归并，不因改角色、昵称、群显示名或头像改变已绑定的记忆归属。

## 群聊上下文：各自独立、公开部分一起看

每个成员使用独立模型会话：会话范围包括群绑定、固定用户身份、角色和权限。群成员与私聊不会因共享长期记忆而共享模型 Thread。

回复当前成员 A 时，输入由四部分组成：当前请求、A 的独立对话、A 有权访问的长期记忆、同群最近的公开消息片段。其他成员的长期记忆和私聊正文不进入公共片段。

公共消息标记发言者、时间和稳定序号，作为待分析资料传入，不授予指令或工具权限。先按群限定，再截取当前请求来源序号之前的有界窗口，不能把生成期间的新消息提前混入。

默认提议：最多最近 30 条且总正文不超过 6000 字符，可配置；按完整消息裁剪。当前请求去重，机器人公开回复可保留。每个成员记录自己已处理的公共序号，避免每轮把同一段公共消息永久追加到独立 Thread。

公共片段按本轮批次的来源序号截取并持久化输入快照。只有确认完整成功的轮次才能推进消费游标；模型是否已接收但结果未知时维持现有不重放原则，不能以游标未前移为由重新执行该轮。换 Thread 后重新提供有界近期片段，不沿用旧 Thread 的消费假设。

## 群聊触发与费用

所有允许收取的群消息都先持久化到公共上下文；先用本地规则确定是否需要生成回复，再请求模型。

- 被 @、明确对机器人的命令／续问：进入个人会话并生成回复，保持现有命令权限边界。
- 普通消息未抽中插话：只入公共上下文，不调用模型，不产生空回复模型轮次。
- 只发表情：从已校准的表情路径投递，无须为了丢弃正文而调用模型；面板不可用时采用明确可见的降级策略。
- 普通插话有每群冷却和可配置请求预算；预算记录与决策原因可在既有工作流查询。被 @ 是否越过预算作为明确配置，默认允许人工主动请求优先。

群内投递仍保持顺序，不能因为成员模型会话独立而并发操作微信 UI。

## 微信真正 @

发件箱把正文和 mention_target 分开保存；mention_target 指向已确认的群 binding 和用户身份，首段回复携带它，后续分段不重复 @。私聊、新闻、普通主动推送不自动添加 @。

发送过程由 wxbot UI 主线程的分步状态机执行：确认目标群与空输入框，触发微信 @ 选择器，按绑定昵称筛选并核对候选，选择目标，核对插入的提及对象，再分批输入正文、核对草稿、回车并确认自己的新气泡。

不根据模型正文中的任意 @ 文本推断投递对象。不把纯文本 @昵称 当成提及成功。找不到对象、重名无法区分、窗口／焦点变化、输入框含用户草稿时，在回车前停止并记录具体原因。

草稿核对需同时识别提及对象标记与正文，不能要求输入框纯字符串等于显示的 @昵称。发送确认分别记录选择提及成功和消息气泡确认；不声称已核验收件人的提醒到达。

现有未完成旧任务需兼容：已开始发送／已提交／结果不确定的任务不重写也不重放；尚未输入的机器人群回复，仅在具有可靠绑定且旧前缀与记录的目标完全一致时转为结构化提及，否则保留并提示人工核对。禁止对任意正文全局删除 @ 前缀。

## 现有工作流补充

不另建日志平台，复用 common.flow_trace、FlowView、WorkflowView 和现有 request / batch / delivery ID。

在现有详情中补充：识别的 user_id / binding_id 与状态、记忆范围及读取条数、公共上下文序号范围与条数、静默或触发原因、@ 选择与校验阶段。默认不把记忆正文、完整检索结果或头像图片写入流程日志。

新增管理操作继续使用 log 的同源检查、显式操作请求头和服务端 Butler 管理凭据；凭据不返回浏览器。模型记忆工具凭据不能调用身份绑定或管理员记忆接口，管理页面也不能通过模型参数选择工具 owner。

公共上下文已归档且未调用模型的消息显示“已归档／静默”，不能显示“模型完成”。头像绑定和记忆编辑从用户详情查看独立业务审计，事件摘要可关联至原有页面。

## 迁移、兼容与运行

- 数据迁移先验证版本并备份；业务数据与队列迁移各自归所属服务，log 的只读页面不触发隐式迁移。
- 不丢弃旧会话、记忆、提醒或排队消息；旧身份到新用户的关联必须明确可审查。
- 保留现有角色、技能白名单、心跳开关和调度。心跳仍只读，不绕过成员记忆范围。
- 不修改个人 Codex 登录、凭证或全局配置；上传图片与运行数据库不提交 Git。
- 不自动重启任何现有服务；交付时列出需用户手动重启的服务。
- 离线测试只用临时业务库、临时队列、假模型与假 UI／剪贴板；不发送真实微信消息。本次开发不延用之前单条真实 @ 测试的发送授权。

## 验收

1. log 可用头像与昵称新建用户，显示不可变 ID 和 0 条记忆；重新加载仍存在，其他配置未变化。
2. 多头像绑定同一用户、改昵称和新增特征均不切断已有记忆；相似头像、同名、未知头像不串人。
3. 群、私聊默认隔离；人工关联后仅共享被明确关联的长期记忆，模型会话仍独立；冲突不静默覆盖。
4. 记忆可分页查询、新增、修正、删除，来源和审计可查看；删改后下一轮不会沿旧 Thread 继续使用旧值。
5. A、B 的独立会话不合并，但 A 的请求能读到同群 B 的近期公开消息，不能读到 B 的长期记忆或私聊；其他群不可见。
6. 静默普通消息不调用模型但可供下一轮上下文使用；消息重试不重复归档，窗口与预算限制生效。
7. 真正 @ 在假 UI 中完成选择和对象核对，候选缺失／歧义／焦点改变／草稿冲突不回车；首段一次提及，私聊和普通推送不增加提及。
8. 实时工作流准确显示归档、识别、召回和提及阶段；生成完成不等于发送成功，不泄露记忆正文。

## 实现者可决定的细节

字段与模块命名、在现有样式系统内的具体布局、图片上限的合理数值、索引与分页实现、测试夹具和标准化特征实现由实现者决定；不得据此改变人工关联规则、业务权限、群上下文边界或消息重放策略。

## 待核对的产品约定

本文将“群聊上下文根据用户隔离开，但是也在一起”解释为成员独立 Thread 加同群公共片段，公共片段默认最近 30 条／6000 字符；这是建议的可配置默认值。

本文把“手工绑定后共享”解释为共享已关联的长期记忆，管理员关联私聊到群身份时须能看清共享范围；独立聊天历史不共享。
