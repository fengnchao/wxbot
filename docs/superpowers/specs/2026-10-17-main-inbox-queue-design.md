# 微信主窗口收件队列与连续消息合并方案

状态：用户已确认，队列实现已写入工作区；离线验证与代码审查记录见对应实施计划。尚未替用户重启运行中的服务。

## 目标与范围

- 默认扫描主微信窗口的全部会话，不要求配置监听用户名单。私聊新消息均进入处理流程；群聊只有明确 @机器人 的消息进入模型队列。
- 不同会话的消息和身份不能混合；同一用户连续发出的多条消息先合并，再交给 Butler/Hermes。
- 等待模型期间继续采集其他会话；同一会话最多一批正在处理；发送统一交回微信 UI 线程。
- 保留角色、skill 白名单、会话身份、群成员标识、时间条过滤和分批键入行为；2026-10-18 按用户反馈将间隔从 1 秒改为 0.5 秒，并增加输入校验。

## 线程和数据流

微信 UI 主线程 → SQLite 收件箱 → 每会话缓冲 → 就绪队列 → 单个模型工作线程 → SQLite 发件箱 → 微信 UI 主线程。

UI Automation 控件、截图、点击和键入只在 UI 线程使用，跨线程传递普通消息数据。工作线程调用 Butler，不持有 UIA 控件。默认一个模型工作线程，按就绪任务顺序处理；采集不等待模型返回。

键入需从阻塞循环改成分步状态机：每批输入后等待的间隔可登记左侧新未读任务、读取当前聊天新增消息；完整输入结束后再切换其他聊天。未点击的会话只能先记录待采集任务，读到正文后才能落库为完整消息。

## 连续消息合并与顺序

- 私聊按会话分缓冲；群聊按群与发言成员分缓冲，并保留每条成员身份。不同人不能合成一段用户发言。
- 默认最后一条消息后安静 3 秒才生成任务；新消息到来时重置此计时。
- 从第一条开始最多等待 10 秒，避免持续发言使任务永远不就绪；达到上限就把已收消息组成一批。
- /reset 等通道命令单独成批，不混入普通问题。
- 缓冲达到条件后才进入就绪队列。B 已发完而 A 仍在补充时，B 可以先处理，不被 A 的缓冲计时挡住。
- 同一会话最多一批执行中。已经开始调用模型后到达的补充进入下一批，沿用同一会话上下文；当前批结束后，其补充排到其他已就绪用户之后，避免一个用户长期占用。
- 第一阶段不取消并重放正在执行的 Butler 请求，以免已经执行的提醒等工具动作重复发生。后续若需合并修订尚未发送的回答，应先区分纯对话与有副作用的任务。

无法准确知道用户是否发完；3 秒安静时间是可调整的默认折中。

## A / B 示例

| 时间 | 事件 | 处理 |
|---|---|---|
| 0 秒 | A：你好 | 进入 A 缓冲 |
| 1 秒 | A：我想问一个问题 | 追加，重新计时 |
| 2 秒 | B：帮我查一下天气 | 进入 B 缓冲，不混入 A |
| 3 秒 | A：问题的补充条件 | 追加，A 安静时间从此刻计算 |
| 5 秒 | B 已安静 3 秒 | B 就绪，可先处理 |
| 6 秒 | A 已安静 3 秒 | A 的三条消息合成一批就绪 |

若模型正在处理 A 时 A 又发了消息，该补充保留为 A 下一批；UI 线程继续采集 B 等会话，按每会话顺序和就绪队列公平处理。

## 持久化与恢复

使用本地 SQLite，消息读取后先事务写入，再认为采集完成。数据库存于运行缓存目录并加入 Git 忽略规则。

- 收件记录：本地消息 id、会话、群成员、接收序号、正文、时间、批次及处理状态。
- 批次记录：batch_id、会话、覆盖的消息序号、合并文本、状态、尝试次数。
- 发件记录：批次、目标会话、回复正文、pending/sending/sent/uncertain 状态。
- 会话状态：消息对齐锚点、已采集/处理序号，支持重启恢复。

去重不能只对正文做哈希，连续两条同样的「你好」都可能是真实消息。当前采集层结合快照重叠与首次未读数量生成本地序号，不具备原生消息 id；完整快照内容完全相同时仍无法区分新增与旧消息。

模型结果落发件箱后才交给 UI 线程。发送前重选目标并核对标题、会话类型与输入焦点；发送后确认消息状态。进程中断时遗留的 sending 记录先核对界面，无法确认则标记 uncertain，不自动重复发送。

Butler 目前的 msg_id 参数尚不构成幂等保证。若要求网络重试也不重复执行工具，需要增加按 batch_id 保存请求状态与结果的幂等处理；结果不确定的请求不能盲目重放。若第一阶段仅改 wxbot，则保留失败/不确定任务供恢复，暂不自动重放可能已执行工具的请求。

## 日志与验证

日志记录发现未读、采集落库、合并计时、批次就绪、模型开始/结束、等待发送、发送确认/失败和恢复情况，并带 batch_id 与会话名，便于关联排查。

验证至少覆盖：A 多条合并；A/B 交错不混合；模型等待时继续收件；同会话不并发；不同群成员不混合；群非提及不调用模型；相同正文不误去重；重启恢复；对象切换阻止误发；不确定发送不重复重放。

## 实际边界

队列可保护已采集并落库的消息，不能让 UI Automation 获得微信未暴露的正文。超出已加载范围的未读消息仍需要后续补读能力；长回复键入期间也需要保存待采集计数。不能仅凭加队列承诺全微信消息 100% 无遗漏。

## 建议第一阶段参数

- 监听全部会话；群聊只处理明确 @机器人。
- 安静合并 3 秒，单批等待上限 10 秒。
- 模型工作线程 1 个，每会话最多 1 个执行中批次。
- SQLite 收件/发件持久化，UI 线程独占微信操作。
- 改动后由用户自行重启需要更新的进程，不自动重启 wxbot 或 Butler。

## 2026-10-18 修复补充

空闲轮询不再滚动或激活微信，仅读取 UIA 暴露的列表行及前台聊天面板；真实收件、发件和恢复核对仍可选择会话。正文改用 Unicode 键盘事件，每批读回校验，回车前将最后读到的新消息入库并刷新确认锚点。保留原模型正文，额外记录已校验的实际输入，用于重启核对。实际输入失败时保留草稿；未确认发件仍不自动重放。
