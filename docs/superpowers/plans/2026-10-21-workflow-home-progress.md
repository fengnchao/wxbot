## 范围与裁定

- 在现有分发分支与工作目录实现，保留全部既有未提交改动，不创建提交。
- 首页独立使用 WorkflowView、workflow.js、workflow.css；现有业务与恢复按钮保留。

- 单条消息一个当前位置；合并后收件卡变批次卡，选择沿收件 ID 继承；已完成卡短暂保留 15 秒。
- Ruling: 500 条活跃记录与 60 轮最近历史分别取样，顶部精确全局计数；超限明确引导原页面分页，避免历史淹没旧任务。
- Ruling: 每次请求完成后等待 1 秒再读取（请求 5 秒超时），采用单请求轮询；不额外引入 WebSocket 连接与服务依赖。
- 无真实服务重启、无微信测试消息。浏览器测试仅使用临时配置、数据库和模拟模型事件。

## 旧进程与新页面混用的启动错误修复

- 用户报告 `app.js:138 renderWorkflow is not defined`。只读实查运行中的 8788 端口：`/assets/workflow.js` 与 `/api/workflow` 均 404，`app.js` 200；磁盘版服务已包含新路由。根因是旧服务进程仍保留旧静态文件白名单，却从磁盘读取新 HTML 与 app.js。
- 复现：测试去掉 workflow.js 后加载其余真实脚本，重现同一 ReferenceError。
- app.js 对可选工作流模块做完整可用性检查；缺失时展示手动重启提示，初始化、切换菜单、刷新、搜索均不会调用未定义函数。其他页面继续可用。
- 工作流 API 404 单独说明需重启 log，不只显示笼统的 HTTP 错误。
- 两份前端检查通过，覆盖脚本缺失、其他菜单可用及接口 404。未操作真实服务进程；加载新 API 仍需用户手动重启 log。
